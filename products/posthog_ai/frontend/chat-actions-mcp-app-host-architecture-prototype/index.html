Contracts at the seams

Action declaration

Before:
{ key, label, kind: "run", message }

After (proposed):
{ key, label, kind: "run", tool, args,
  destructive, binding }

Selection stays with suggest-actions. The server binds the tool and arguments to the offering result, current project and authorized caller. A label or an app request does not grant permission.

Host interface

ui resource + tool result → sandboxed app

App → tools/call { name, arguments }
Host → validated CallToolResult

App → ui/update-model-context
Host → next-turn state snapshot

Credentials stay in the host/backend. Writes require authorization and confirmed arguments. Only allow declared tools and UI resources. Unknown targets fail closed.

Flows

Read: agent calls the offering tool → result declares app resource → host fetches HTML → sandbox initializes → host sends structured result → app shows actions.

Write: user confirms → app requests tools/call → host validates tool, bound project and permission → MCP server calls product API → host records canonical outcome → app shows success → next user turn includes outcome context.

Failure: product rejects an unverified sender → tool returns isError → app shows error and Try again in place → host records the failed attempt. A timeout after an uncertain write must reconcile status before retrying.

Data, caching and performance

Production needs a durable outcome record keyed by project, task/run, offering tool call and action instance. Reloads replay the canonical result and restore spent buttons. The demo keeps records in memory and Reset clears them.

ui/update-model-context replaces the latest state for one app. It is not an append-only audit log. The host stores verified tool outcomes separately and supplies them to the next turn. App state remains untrusted context.

Cache versioned app HTML/assets by resource URI, not by user credentials. Do not cache permission decisions or tenant results across callers. Lazy-load the host SDK and resource only for app-bearing tool calls. One click adds one backend tool request and one outcome write.

Decision cards

Locked by Michael · 2026-10-07 · option A

How does PostHog's host execute a tool?

A. Session-authenticated backend proxy to the MCP server. Keep one tool implementation. Backend fixes project and caller, grants only the necessary scopes, and never returns credentials to the app. Adds a transport and auth seam requiring security review.

B. Bridge MCP tool names to native typed browser adapters. Smaller first workflow integration, but duplicates tool routing and behavior for each product.

Michael selected A through the question tool. This replaces the transport decision from the native prototype; the existing token-minting helper alone does not prove the permission model.

Where do follow-up controls live?

A. One small suggested-actions MCP App. Preserve buttons below the answer; shared controls can grow to typed forms. Start with one workflow action and a clear result summary.

B. Put controls in each product's detail app. Richer context, but requires changing every product app and may add a large card where two buttons suffice.

Michael selected A through the question tool. Product apps can adopt the shared controls when richer configuration is needed.

Locked by Michael's accepted native prototype

Direct execution without an agent turn; inline confirmation; success/error shown in place; canonical outcomes replay after reload; the next turn learns the result; bound tool arguments. Native composer insert/send behavior remains host-specific.

Blast radius and proof limits

Production touches the tool advertisement/visibility rules, result metadata through exec, iframe sandbox and CSP, server execution authorization, run history and hidden context. Gate the new host behind a feature flag and retain native/text fallbacks. The existing permission card remains for agent-originated tool calls.

This demo verifies the interaction and a subset of the protocol. It does not use the SDK, provide production sandbox isolation, prove authenticated RBAC or CSRF, persist across reloads, or certify live Claude/ChatGPT rendering. Production must use the official AppBridge transport and validate the real resource under enforced CSP.
