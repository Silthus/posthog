1. Question

In v1, a run button sends Enable workflow <id>. as the user's next turn, and the agent calls workflows-enable in that turn. The new destination is that the click runs the tool itself, with the user's own session and permissions, shows a confirmation and then the result in place, as if the user had clicked "Enable" in the product. No chat message sits in between. The agent learns the outcome before its next turn. The element is a primitive that products extend: a button now, then selects, dropdowns and forms. This brief designs that primitive across services/mcp, the PostHog AI thread, product frontends and Django, and lists every fork as a decision card.

The finding that shapes the design

  • workflows-enable is only PATCH /api/projects/:id/hog_flows/:id/ {status: 'active'} (services/mcp/src/tools/workflows/lifecycle.ts:14-34).
  • The browser already has that call, typed and session-authed: hogFlowsPartialUpdate (products/workflows/frontend/generated/api.ts:326), with a zod body schema (api.zod.ts:1281).
  • Session requests skip token scopes but keep team membership and RBAC access control (posthog/permissions.py:834). This is exactly the "Enable in the product" path.
  • Products already register per-tool UI in one manifest, keyed by MCP tool name (frontend/src/posthogAiToolRenderers.ts, ToolRegistryEntry in products/posthog_ai/frontend/components/tool/toolRegistry.tsx:47).

So the recommended design adds a browser adapter for a tool to that same registry entry. The tool then has two adapters at one seam ("run tool X with args"): the MCP server, used by the agent, and the browser, used by a click. Both render through the same product Renderer.

3. Contracts

3.1 The declaration in tools.yaml (services/mcp)

Before (v1, #111860)
actions:
  - key: enable
    label: Enable the workflow
    kind: run
    tool: workflows-enable
    message: Enable workflow {id}.
After
actions:
  - key: enable
    label: Enable the workflow
    kind: run
    tool: workflows-enable
    args:
      id: '{id}'        # slot, bound from this tool's result
    # control: button   # default; select/form later (card 4)
  • Invariant: a run action has tool and args, and no message. insert and send keep message and do not change.
  • Invariant: every {slot} in args is bound through the existing slot provenance check. An unbound slot drops the action into errors, as in v1.
  • Codegen check: every run target tool needs a browser adapter in the frontend registry (card 1). A Jest test asserts this against the generated tool definitions, in the same way as test_generated_files_are_registered.py.

3.2 suggest-actions output

Before
{ actions: [{ key, label, kind, message }],
  errors:  [{ key, reason }] }
After
type SuggestedAction =
  | { key; label; kind: 'insert' | 'send'; message: string }
  | { key; label; kind: 'run';
      tool: string;                      // 'workflows-enable'
      args: Record<string, Json>;        // { id: 'wf_8f2c' }
      destructive: boolean }             // from the target tool's annotation

{ actions: SuggestedAction[], errors: [{ key, reason }] }
  • Action identity is <suggest-actions toolCallId>:<key>. It is stable across reloads, so an outcome attaches to its button.
  • Error mode: the target tool is not visible to the caller (flag or scope), so the action goes to errors, as in v1.

3.3 The browser adapter (new, on ToolRegistryEntry)

// products/posthog_ai/frontend/components/tool/toolRegistry.tsx
export interface BrowserRunContext { projectId: string }

export interface BrowserRun<Args extends z.ZodTypeAny = z.ZodTypeAny> {
    /** Validated before any request. Prefer the generated api.zod.ts schema. */
    args: Args
    /** Runs the tool's effect with the user's session, through the product's generated API client. */
    execute: (args: z.infer<Args>, context: BrowserRunContext) => Promise<unknown>
}

export interface ToolRegistryEntry {
    key: string
    Renderer?: ToolRendererComponent
    PermissionPreview?: ...      // reused as the confirm body (card 3)
    browserRun?: () => Promise<BrowserRun>   // NEW, lazy like Renderer
    ...
}

// products/workflows/frontend/posthogAiToolRenderers.tsx (new file)
export const posthogAiToolRenderers: ToolRegistryEntry[] = [{
    key: 'workflows-enable',
    displayName: 'Enable workflow',
    icon: <IconPlay />,
    requiresPostHogOrigin: true,
    browserRun: () => import('./posthogAi/enableWorkflow').then((m) => m.enableWorkflow),
}]

// products/workflows/frontend/posthogAi/enableWorkflow.ts (new file)
export const enableWorkflow: BrowserRun = {
    args: z.object({ id: z.string() }),
    execute: ({ id }, { projectId }) => hogFlowsPartialUpdate(projectId, id, { status: 'active' }),
}

Declaration modules use type-only imports from api/tools and load behaviour lazily (frontend guide §2), so the adapter sits behind a dynamic import like a Renderer.

  • Invariant: the adapter has the same effect as the MCP tool. It may skip MCP-only presentation, such as _posthogUrl enrichment. The renderer must accept both result shapes, or the adapter adds the URL itself.
  • Error modes: zod failure (no request, button shows the error), 403 (RBAC), 404, 400 (validation), network. Each becomes a failed outcome with the API's own message.
  • Performance: one product API request per click. No new server.

3.4 The outcome record (new Django endpoint, run log entry)

POST /api/projects/:project_id/tasks/:task_id/runs/:run_id/chat_action_outcome/
{ action_id: "toolu_01AbC:enable",
  tool: "workflows-enable",
  args: { id: "wf_8f2c" },
  status: "succeeded" | "failed",
  summary: "Workflow Weekly digest is now active",   // ≤ 500 chars, shown to the agent
  result?: Json,                                      // ≤ 16 KB, for the in-place card on reload
  error?: string }

// appended to the current run's JSONL log:
{ notification: { method: "_posthog/chat_action_outcome", params: { ...body, user_id, ran_at } } }
  • Trust: the browser reports its own result. The record is user-asserted. It never authorizes anything. The agent receives it only as untrusted context (3.5).
  • Invariant: the endpoint checks that the user can access the task run and that action_id names a suggest-actions call in the run's resume chain.
  • Why the tasks run API: the surface couples to task runs by design and must not import the conversations API (products/posthog_ai/frontend/CLAUDE.md §2).
  • Replay: runStreamLogic folds outcomes onto their button by action_id, latest wins. The current projection ignores unknown _posthog/* methods, so older clients are not affected.

3.5 Agent sync (hidden context on the next user message)

// a provider on attachedContextLogic, fed from runStreamLogic's folded outcomes
registerContext('chat-action-outcomes', outcomes.map((o) => ({
    type: 'chat_action_outcome',
    key: o.action_id,
    label: `${o.tool} ${o.status}`,
    value: JSON.stringify({ tool: o.tool, args: o.args, status: o.status, summary: o.summary }),
    hidden: true,
})))
  • This reuses the live attached-context contract (products/posthog_ai/frontend/types/contextTypes.ts:6). wrapWithPosthogContext renders it into the untrusted block. Replay already strips that block.
  • Invariant: an outcome reaches the agent exactly once, with the first user message after it. The existing dedupe does this for free: seenContextLinesByTask prunes any keyed item already sent anywhere in the resume chain, and it survives reloads.
  • Gap: if the agent is mid-turn when the click lands, it learns the outcome only on the next turn. Today buttons render only after the turn ends.

3.6 Element schema, later controls (sketch for card 4)

type ArgSource =
  | string                                  // literal or '{slot}', agent-filled and provenance-checked
  | { input: 'select'; options: '{slot}' }  // the user picks from a list the agent bound
  | { input: 'text' | 'email' | 'number' } // the user types it

type ChatActionControl = 'button' | 'select' | 'form'
// button: every arg is bound. select: one arg is { input: 'select' }. form: any arg is { input }.
// Field types come from the browser adapter's zod schema, so the form validates what execute() takes.

5. Data

  • No schema change and no migration. The outcome is a new _posthog/chat_action_outcome method in the run JSONL log, which already holds _posthog/user_message and _posthog/permission_* entries.
  • The log of a terminal run still accepts appends through TaskRun.append_log (products/tasks/backend/models.py:2862). Thread history includes ancestor runs, so outcomes survive a successor run.

6. Caching and performance

Nothing is cached. A click costs one product API request plus one log append. The hot path (stream replay) gains one fold over a method it already parses. No load concern.

7. Decision cards

OPEN

1. Execution path: how a click runs the tool

  • A. Browser adapter on the tool's registry entry (product calls its own generated API with the session). Pros: the real "Enable in the product" path. Session auth and RBAC with no new auth surface. Typed. The product owns it next to its renderer. Cons: one small adapter per runnable tool. Compound MCP tools need an equivalent written in the browser. The adapter can drift from the MCP tool, so a registration test guards it.
  • B. Django proxy into services/mcp with a token minted per click for the session user (mint_oauth_access_token, posthog/models/oauth.py:657): tool scopes only, one team, 60 s lifetime. Pros: generic, runs the exact MCP tool for any of about 1,000 tools, no product code. Cons: a session endpoint that mints tokens is a security danger area. It needs a new Django to MCP call path, which does not exist today. Scope translation can over-grant.
  • C. Sandbox command (new verb on the run command relay). Cons: needs a live sandbox, and it runs with the run's token, not the clicking user's permissions. Reject.
  • D. Reimplement in Python behind mcp_tools. Cons: duplicates generated handlers. Reject.
Recommendation: A now. It matches the wording exactly ("as if they clicked Enable in the product") and stays small. B is the later fallback for tools without an adapter. It is a third adapter at the same seam, so A does not block it.
OPEN

2. Agent sync: how the agent learns the outcome

  • A. Outcome in the run log, plus a hidden context item on the next user message (3.4, 3.5). Pros: reuses the attached-context contract and the log. Pending state comes from the log. No agent release. Cons: the agent learns it on the next turn, not at once. The record is user-asserted, so it goes in the untrusted block.
  • B. Synthetic tool call and result inside the live ACP session. Pros: the agent sees it as its own tool call. Cons: needs a new agent-server contract and a @posthog/agent release. Session hydration needs matching ids.
  • C. No sync. The agent re-reads state when it needs to. Pros: nothing to build. Cons: the agent does not know to re-read, and it may offer "Enable" again.
Recommendation: A. Buttons render only between turns, so "next turn" is the only time the outcome matters.
OPEN

3. Confirmation UX before and after a destructive call

  • A. Inline confirm in place. The button expands into a small card. The body is the product's PermissionPreview when one exists, otherwise the label plus args. It has Confirm and Cancel. Then the card shows a spinner, then the result card or the error. It appears only when the target tool is destructive. Pros: in place, one click for safe tools, the same preview as the permission card. Cons: a second preview surface to keep consistent.
  • B. Reuse the permission card in the composer area. Cons: PermissionInput belongs to an agent-owned request (requestId, toolCallId, reply to the sandbox). It is not in place, and it needs a live run.
  • C. Modal dialog (LemonDialog). Pros: familiar product pattern. Cons: leaves the thread context. It is not "in place".
Recommendation: A. The permission card stays the gate for calls the agent makes (toolPolicy.ts). A click is the user's own act, so the inline confirm is its gate. This keeps the map rule "a button that writes goes through the same approval a typed request would" without coupling to the agent's request lifecycle. After success the button is spent. After a failure it offers "Try again".
OPEN

4. Element schema and where args come from

  • A. Button now, with every arg agent-filled and provenance-bound. Later controls declare user-filled args (3.6). Field types come from the adapter's zod schema. Pros: smallest v1, and selects and forms extend it without a new contract. Cons: a form needs a renderer per input type later.
  • B. A json-render component catalog now (Zod prop schemas per component, the agent composes them). Pros: the full Vercel pattern. Cons: generative UI, which the map rules out of scope. Large.
  • C. Form generated from the target tool's JSON schema (the generative UI research recommendation), shown for every run action. Pros: general. Cons: every click becomes a form. Bad for "Enable".
Recommendation: A. It keeps the research's typed form as the form control later, and the field types come from the same zod schema the adapter validates.

9. Blast radius

  • What can break: a wrong adapter writes the wrong thing with the user's session. The user can only do what they could already do in the product, and destructive tools confirm first.
  • Who notices: the user, in place, and the activity log, which records the change under the user, the same as a product click.
  • Isolation: everything sits behind posthog-ai-chat-actions. Older clients ignore the new log method. The agent runtime does not change.
  • Out of scope: the generic proxy (card 1 B), generative UI, external MCP hosts (#272 renders there through MCP apps and app.callServerTool), and the legacy runtime.
