1. Question

Code in a project calls posthog.emails.send({ from, to, subject, html, text, replyTo, cc, bcc, distinctId }) with a project secret API key (phs_), and one transactional email arrives. The map (#461) settles the approach: each send runs as one invocation on the team's hidden "API sends" workflow, owned by the API the way broadcasts and loops own their workflows through origin_product, so billing, quota, metrics, pausing and the Workflows logs work unchanged. This brief shapes the contract along that path: the Django endpoint (auth, scope, flag, idempotency, throttles), how the hidden workflow is found or created and kept out of the workflow list, the Django → CDP call (a scoped service JWT, no new INTERNAL_API_SECRET caller), how the payload lands in the existing email step and email queue, what the call returns, and where every agent-facing error code comes from.

Destination: the contract that the implementation tickets after this one build, test-first, behind a backend flag.

2. Glossary

TermMeaning
API sendOne email sent by one POST to the email endpoint. One API send is one hog flow invocation.
API sends workflowThe one hidden HogFlow per team with origin_product = "api_sends": trigger → one transactional email step → exit. Created by trusted code on the first send, never by a user.
Default senderTeamWorkflowsConfig.default_email_integration_id (products/workflows/backend/models/team_workflows_config.py:56), a plain id of an email integration.
Verified senderAn email Integration with config["verified"] == True (set by DNS verification, posthog/models/integration/email.py:83; checked at send time in email.service.ts:943).
Send idThe id the call returns. It is the hog flow invocation id (a UUIDT), minted by Django so that a retry after a timeout reuses it.
Accepted / rejectedAccepted: the invocation is on the hogflow queue. Rejected: a synchronous error with a code from section 9. Everything after acceptance (suppression, bounce prevention, provider errors) is asynchronous and shows in the workflow logs and delivery events, not in the HTTP response.

Invariants.

  • Exactly one live API sends flow per team. A partial unique index on (team_id) WHERE origin_product = 'api_sends' makes a duplicate impossible; get_or_create under that constraint makes concurrent first sends converge (card C8).
  • Only trusted code creates or edits it. The hog flow serializer already refuses to change origin_product after create (hog_flow.py:3149-3155); the update path also refuses edits to an api_sends flow's graph.
  • The flow's graph is owned by code. When the code shape changes, get_or_create rewrites the graph on a version mismatch, so no data migration is needed.

New: a per-team singleton. Broadcasts and loops create one flow per broadcast or loop (products/workflows/frontend/Broadcasts/broadcastWizardLogic.ts:1989, products/desktop/packages/ui/src/features/loops/loopHogFlowMapping.ts:279), from the client, and nothing deduplicates them. The model's only constraint is (team, version, id) (hog_flow.py:128). A singleton that trusted backend code creates is new, so card C8 decides how it stays single.

Out of the list, in Workflows. The workflow list filters by type through workflow_type_q (products/workflows/backend/services/hog_flow_reads.py:388-405), and the Workflows page asks for messaging, automation and loop (products/workflows/frontend/Workflows/workflowsLogic.ts:25). Adding "api_send": HogFlow.OriginProduct.API_SENDS to OWNED_WORKFLOW_TYPES keeps the flow out of that page, the way broadcasts already leave it. A client that lists without a type filter still sees it; the update path refuses edits to it. Its sends stay visible in the normal flow page (metrics, logs, invocation results). There is no Workflows UI entry in this map: a person opens the page by a direct link (card C9), and card C16 decides where that link comes from.

Pausing and quota. Because it is a normal hog flow, the per-workflow email pause (email_sending_paused_at on the model), team suspension, the team sending-tier cap and pacing all apply unchanged in the email worker (email.service.ts:405, :437, :530, :556), and the hogflow worker cancels a run whose flow is not active (consumers/cdp-cyclotron-worker-hogflow.consumer.ts:105). Billing quota does not apply by itself: it is checked only on event-trigger admission (hog-flow-invocation-pipeline.service.ts:195), and the scheduled route skips it. The new route runs the same check, checkHogFlowQuotaLimits (nodejs/src/cdp/services/hogflows/hogflow-quota-limiting.ts:23), before it enqueues (card C15). Paused and quota-limited sends are rejected in the response, not only logged.

def create_hog_flow_api_send(team_id: int, hog_flow_id: str, send: ApiSendInvocation) -> requests.Response:
    token = WORKFLOWS_API_SEND_JWT_PURPOSE.mint({"team_id": team_id, "hog_flow_id": hog_flow_id})

        json=send.to_json(),

Invariants. The token is pinned to one team and one flow, and lives two minutes. The route accepts only a flow with origin_product = "api_sends", so a token cannot start any other workflow. The invocation id comes from Django, so a Django retry after a timeout enqueues nothing new (card C11).

Error modes. 401 bad token, 404 team or flow, 402 quota limited, 423 paused, 400 schema, 500 queue error. Django maps 402 to quota_limit_exceeded, 423 to sending_paused, and every other non-200 and every timeout to 503 send_service_unavailable, keeps the idempotency reservation on a timeout, and releases it on a definite failure, the same way hog_flow.run does.

Performance. One Postgres write to the cyclotron queue plus one lifecycle row, the same cost as a scheduled invocation. Sending happens later in the email worker, so the HTTP call stays fast and does not wait for SES.

7. Payload → email step → email queue

The flow's one email step is the existing function_email action (nodejs/src/cdp/schema/hogflow.ts:228-253) on template-email (nodejs/src/cdp/templates/_destinations/email/email.template.ts, code sendEmail(inputs.email)). Its config sets message_category_type: "transactional", which is what the email worker reads (email.service.ts:873, :1128) to drop unsubscribe headers and skip opt-out checks, and what email-priority.ts:21-37 reads to put the send on the fast lane. Suppression still applies (recipient-preferences.service.ts:108).

Its email input reads every field from the invocation's variables. Liquid escapes output by default (nodejs/src/cdp/utils/liquid.ts:93, outputEscape: 'escape'), so every field uses | raw, or a subject like "Tom & Jerry" would arrive as "Tom &amp; Jerry".

Status later. The send id is the invocation id, so with no new storage:

  • The API sends workflow's logs use the invocation id as instance_id (hog-function-monitoring.service.ts:175; filter at posthog/api/log_entries.py:108), so Workflows shows each send, including asynchronous outcomes (suppressed, bounce prevented, provider error).
  • An endpoint already returns one invocation's result: GET /hog_flows/{flow}/invocation_results/{invocation_id} (products/workflows/backend/presentation/views/hog_flow.py:5795-5805), with running, succeeded, failed, canceled. "Succeeded" means the run finished, not that the email was delivered (hog-invocation-results.service.ts:565). It needs hog_flow:read, not the send key.
  • With distinctId, the delivery events ($workflows_email_sent, _delivered, _opened, _link_clicked, _bounced, _blocked, _failed; names at email-tracking.service.ts:92-100, emitted at email.service.ts:689-712) land on that person, so the customer queries them like any event.
  • A GET /emails/{id} status endpoint is not in this slice (card C14).

11. Data, caching, performance

  • Schema: one new HogFlowOriginProduct choice (no column change, origin_product is a CharField), and one partial unique index on posthog_hogflow (team_id) WHERE origin_product = 'api_sends' (card C8). The index ships as its own migration PR, built concurrently.
  • No new table. Idempotency lives in the cache (card C4); status lives in the existing invocation results and events.
  • Cache keys: email_api_send:{team_id}:{idempotency_key}, 24 h. Throttles use the existing psak:{key_id} and psak-team:{team_id} buckets.
  • Hot path per send: one cache add, two small indexed reads (integrations, team workflows config), one hog flow read (cache it per team for a minute), one HTTP call to CDP, one queue insert. No ClickHouse read.
  • First send per team: one extra insert to create the flow, then the CDP flow manager loads it on its next reload. The route must load a flow it has not cached yet (card C7 notes it).

C16 · Where the direct link to the API sends workflow comes fromopen

C9 leaves no Workflows UI entry, and the flow id differs per team, so a person needs the link from somewhere.

  1. The accepted response carries it: 200 { "id": ..., "url": "https://…/project/{id}/workflows/{flow id}/invocations" }, and posthog-node returns it in data.url.
