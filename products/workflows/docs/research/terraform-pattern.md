# What the Terraform provider pattern already answers for workflows as code

Research for [ticket 97](https://github.com/Silthus/posthog/issues/97) on [map 68](https://github.com/Silthus/posthog/issues/68). Sources: this repo's `terraform/` tree and `frontend/src/lib/components/TerraformExporter/`, and the public [`PostHog/terraform-provider-posthog`](https://github.com/PostHog/terraform-provider-posthog) repository (fetched via the GitHub API and raw content, since `registry.terraform.io` did not render through WebFetch).

## 1. Push and sync

A Terraform-managed resource is created by `terraform apply` running `POST` against the PostHog API, and updated by `PATCH` on drift between config and state (`docs/index.md`, `docs/resources/hog_function.md`, both in `terraform-provider-posthog`). Identity is the resource's own database id or UUID, stored in Terraform state, not a user-chosen key: `posthog_feature_flag` reads back a numeric `id`, `posthog_hog_function` a UUID (both resources' `docs/resources/*.md`, "Read-Only" section). The one exception is `posthog_feature_flag`'s `key`, which is required config, not state-derived identity — the provider still keys imports and API calls off `id`, not `key`.

Drift detection is Terraform's standard state-vs-config diff: `terraform plan` reads the resource from the API and compares it to the config before deciding to update. The CHANGELOG documents provider-specific edge cases in this loop: `posthog_alert`'s `schedule_restriction` now round-trips every update because unmanaged quiet-hours changes must surface as drift (CHANGELOG.md, "Upgrade notes", unreleased), and `posthog_feature_flag.filters` is compared semantically with an `ignore_filter_fields` allow-list so other products (Experiments, Early Access Features) writing into the same JSON blob don't produce permanent diffs (`docs/resources/feature_flag.md`).

This repo's own `terraform/` tree (`terraform/us/project-2/team-analytics-platform/dashboard-key-metrics/dashboards.tf`) uses the provider this way in production: an `import` block plus a `resource` block per pre-existing object, run through Terragrunt.

## 2. CI step

This repo has a documented, working job: `.github/workflows/terragrunt-posthog.yaml`. It triggers on `pull_request` and `push: branches: [master]` scoped to `terraform/**/*`, discovers every `team-*` module via `find` + `jq`, and fans out a matrix job per module. On a PR it runs `terragrunt plan -detailed-exitcode` and comments only when there's a diff (deleting stale bot comments first); on `master` it runs `terragrunt apply -auto-approve`. Auth to AWS (for the S3 state backend) goes through `aws-actions/configure-aws-credentials` with OIDC (`role-to-assume`), and the PostHog API key is a repo secret (`POSTHOG_PROVIDER_POSTHOG_API_KEY`) injected as an env var. This is a real, working precedent for "plan on PR, apply on merge" — not just documentation.

## 3. Auth

The provider takes `api_key` (String, Sensitive) in the `provider "posthog" {}` block or `POSTHOG_API_KEY` env var, described only as a "PostHog personal API key" (`docs/index.md`). No scope list is documented anywhere in the provider's docs or README — the acceptance-test setup (`README.md`) just sets `POSTHOG_API_KEY`, `POSTHOG_PROJECT_ID`, `POSTHOG_HOST`, `POSTHOG_ORGANIZATION_ID`. **Unverified**: whether the provider ever documents required scopes per resource; nothing in `docs/` breaks auth down by scope the way the workflows CLI's `hog_flow:write` does. In this repo's own usage the key is a GitHub Actions secret (`POSTHOG_PROVIDER_POSTHOG_API_KEY`), never a file on disk.

## 4. Rollback

Nothing PostHog-specific: the provider carries no rollback feature. Rollback is whatever Terraform itself offers — state history via the configured backend (this repo's is S3 with `use_lockfile = true`, `encrypt = true`, no versioning flag set in `terraform/root.hcl`, so **unverified** whether state versioning is enabled at the bucket level) — or reverting the `.tf` file in git and re-running `apply`, which is exactly the git-revert-plus-apply path the CLI design already uses. The CHANGELOG's HTTP-retry fixes (`CHANGELOG.md`, "Fixes", unreleased) are the closest thing to rollback-adjacent guidance: a `POST`/`PATCH` that times out is deliberately never replayed, and the error message now says so, "so you can check before re-running rather than risk a second resource" — i.e. the provider's answer to a failed apply is "look before you retry," not an automated rollback.

## 5. Breaking changes

Users learn about a breaking change from the provider's own `CHANGELOG.md`, specifically its "Upgrade notes" subsection, and from `terraform plan` output showing an unexpected diff after upgrading the provider version. Two concrete precedents in the unreleased section: raising the per-request retry timeout from 30s to up to 2 minutes, and `posthog_alert` now sending `schedule_restriction` on every update (so any quiet-hours state set outside Terraform "will show as a removal on the next plan" unless added to config). Versioning is plain semver-looking 1.0.x tags (`v1.0.0` through `v1.0.21` via GitHub tags/releases) with no major-version bump yet, so there's no precedent here for a major-version breaking-change convention — only changelog prose plus plan-time diff. There is no PostHog precedent (in this provider or elsewhere found) for warning a **user**, at apply/push time, that a specific change will break something currently running — the alert case above is closest, but it's a config-diff surfacing mechanism, not a runtime-impact warning like the UI's `publish_impact`.

## 6. Several projects (dev, staging, prod)

Both the provider and this repo's own usage handle multi-project through a per-resource `project_id` override, not separate credentials or repos: nearly every resource schema (`feature_flag.md`, `hog_function.md`) documents an optional `project_id` (String) that "Overrides the provider-level project_id." This repo's `terraform/` tree structures it by directory instead: `terraform/us/` (region) → `terraform/us/project-2/` (a project, injecting `posthog_project_id` via `variables_project.tf.tpl`) → `terraform/us/project-2/team-<name>/` (a team) → per-module leaf directories, using Terragrunt's `include`/`inputs` inheritance so each project's key and id flow down without repeating provider blocks. Secrets (the API key) are injected once per apply, per Terragrunt "region," via `get_env(...)` reading the CI secret — the same key can apply across every project it's scoped to, since the provider doesn't require a separate key per project.

## Comparison with the locked CLI design

| Question         | Terraform provider pattern                                                                                                           | Workflows CLI (locked, map 68)                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Identity         | Server-assigned `id`/UUID in state; `feature_flag.key` is required config but not the lookup key                                     | Client-chosen `key`, unique per team, no write-back needed                                                                   |
| Sync detection   | Full state-vs-config diff every plan, exceptions hand-coded per field (`ignore_filter_fields`, forced `schedule_restriction` resend) | Explicit `check`/`push` comparing source-derived projection against remote's writable fields                                 |
| CI step          | One real, working matrix job: `plan` on PR (comment on diff), `apply` on merge to master                                             | One documented job planned, not yet built (`Not yet specified`)                                                              |
| Auth             | Personal API key, undocumented scope, env var or provider block                                                                      | `hog_flow:write` personal API key, scoped, from `~/.posthog/credentials.json` or `POSTHOG_CLI_API_KEY`                       |
| Rollback         | Terraform's own state history / git-revert-plus-apply; provider adds only "don't blindly retry a failed write"                       | git-revert-plus-push, no state file to reconcile since there's no local state — the CLI is stateless besides the source file |
| Breaking changes | Provider CHANGELOG "Upgrade notes" + plan-time diff; no runtime-impact warning                                                       | Open (fog): `check`/`push` impact warning, sharpened by this research per map 68's Notes                                     |
| Multi-project    | Per-resource `project_id` override, one key applies broadly                                                                          | `POSTHOG_CLI_PROJECT_ID` per project, matching the CLI's per-invocation scoping                                              |

Where the CLI design **can reuse** the pattern: the plan/apply-shaped CI job (this repo's `terragrunt-posthog.yaml` is a directly liftable shape — matrix discovery, plan-and-comment on PR, apply-on-merge — even though workflows has no state file to plan against); and the "don't replay a `POST`/`PATCH` after an ambiguous failure" retry discipline, which applies just as well to a stateless CLI push.

Where it **should not**: server-assigned, state-tracked identity (map 68 already ruled this out — `key` was chosen specifically to avoid write-back and a state file); undocumented/broad-scope API keys (the CLI's scoped `hog_flow:write` key is already tighter); and full field-level diff-as-drift-detection, which requires a persisted state file the CLI deliberately doesn't have.

## Verdict

A Terraform provider resource for workflows is not a cheaper route than the CLI here. Terraform's value is managing resources Terraform already owns end-to-end via state — the provider pattern above spends real, ongoing complexity (state backend, drift reconciliation, `ignore_filter_fields`-style hand-tuned diffing, per-provider-version changelog discipline) to get generic plan/apply semantics for infrastructure-shaped resources like dashboards and alerts. Workflows as code, as map 68 has scoped it, is source-of-truth-in-git with no two-way sync and no state file by design (code-owned means read-only in the UI, the next push wins) — that's a narrower problem than Terraform solves, and building a provider would mean adopting Terraform's whole state-management machinery to get less than the CLI already gives: typed authoring via the SDK, `key`-based identity with no write-back, and a push model that doesn't need drift detection because the UI can't diverge from it. The one thing worth lifting is the CI job shape, not the provider mechanism.
