# Which MCP tools let an agent verify an email sender on its own?

Ticket: [Silthus/posthog#462](https://github.com/Silthus/posthog/issues/462), child of the map [#461](https://github.com/Silthus/posthog/issues/461).
Checked against `upstream/master` at `f7a60dd0c7a` (2026-10-14) and the open PR state on `PostHog/posthog` and `Silthus/posthog` on the same day.

## Answer

- **No. On `PostHog/posthog` master an agent cannot verify an email sender through the PostHog MCP at all.** None of the four steps (create the sender, read the DNS records, apply or check them, confirm verification) has an MCP tool, and the REST routes behind steps 2 to 4 reject scoped API keys and OAuth tokens.
- **The tools exist, but only as an open draft.** [Silthus/posthog#343](https://github.com/Silthus/posthog/pull/343) adds five MCP tools, scope changes, schemas and a `setting-up-an-email-domain` skill, behind the server flag `workflows-email-domain-agent-setup`. Its upstream copy [PostHog/posthog#109703](https://github.com/PostHog/posthog/pull/109703) is closed. **No PR carrying these tools is open on `PostHog/posthog` today**, so #343 still has to move from the fork to upstream.
- **#343 is conflicting.** It shows `CONFLICTING` / `DIRTY` and its last CI run on the fork had failures. Master has since changed the same area (default reply-to on `NativeEmailIntegrationSerializer`, [#115898](https://github.com/PostHog/posthog/pull/115898); default sender, [#114682](https://github.com/PostHog/posthog/pull/114682)). It needs a rebase before it can be recreated upstream.
- **Consequence for the map.** The slice-1 skill cannot tell an agent to "verify a sender through the PostHog MCP" until #343 (or a trimmed version) lands upstream and its flag is on for the project. A task to land those tools comes before the spec, or the skill must say plainly that verification currently happens in the PostHog UI.
- **One more gap remains after #343.** The PostHog MCP never writes DNS. The agent either hands the person a Domain Connect URL to approve, or uses its own DNS tooling (another MCP server, a provider CLI). If it has neither, the person adds the records by hand.

## What #343 gives an agent

Behind `workflows-email-domain-agent-setup` (server flag, default off), per its description:

1. `integrations-email-create` creates the sender and registers the domain.
2. `integrations-email-verify-create` returns DNS records with per-record status and verifies. The agent calls it until `status` is `success`.
3. `integrations-domain-connect-check-retrieve` says whether the DNS host supports one-click setup.
4. `integrations-domain-connect-apply-url-create` returns a URL the person approves at their DNS host.
5. `integrations-email-partial-update` edits the display name or MAIL FROM subdomain.

Plus the `setting-up-an-email-domain` skill (`products/workflows/skills/`) and a sandboxed eval suite (`eval_email_domain_setup`) that runs an agent with the skill against simulated SES and DNS.

The flag also gates the token access itself. With the flag off, scoped keys and OAuth still get the rejection. The map's own backend flag for the email send API is separate, so the slice-1 skill has to account for two flags.
