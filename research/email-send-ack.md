# Does an email-send acknowledgement mean durably queued?

Research for [Research whether a send answer means the email is durably queued](https://github.com/Silthus/posthog/issues/523), in the [code-managed email map](https://github.com/Silthus/posthog/issues/461). Source audit, 2026-10-20. No product code changed and no runtime or deployment guarantee inferred from a mocked test.

## Answer

**The positive acknowledgement already follows an acknowledged Postgres enqueue. It is `202 Accepted`, not `200 OK`. It does not mean that SES accepted the email, that a recipient server accepted it, or that it reached an inbox.** The job is an invocation in Cyclotron v2's Postgres `cyclotron_jobs` table, on the `email` queue's fast lane. Kafka carries monitoring/results/events separately; it is not the acceptance queue for this route. [F-send] [F-cdp] [M-wiring] [M-queue] [M-insert]

**An error is not proof that nothing was queued.** A database commit can precede a lost response or Django's ten-second timeout. Neither the route nor the SDK supplies send idempotency today. Repeating an ambiguous send can create another invocation and another email. [F-service] [F-client] [M-id] [N-transport]

**“Every later failure reaches the developer” is not true today.** Some no-send outcomes are successful workflow executions with a skip metric and log, not failed invocations. Person events are opt-in, not emitted for all skips, and do not carry the returned message ID. Normal result/event publication is best-effort after the queue job is settled. There is no email-specific status method or delivery callback in this SDK. [M-skips] [M-policy] [M-terminal] [M-worker-flush] [M-capture] [N-send]

The smallest useful contract is:

> A successful send result means PostHog acknowledged storing the invocation for asynchronous delivery processing. It does not confirm provider acceptance or delivery. A failed or timed-out request may have been accepted. Retry with the same idempotency key once that facility exists. Use the returned message ID to observe delivery processing and provider feedback once a durable status surface exists.

The first sentence describes today's positive path. The idempotency and durable status facilities in the last two sentences are **proposals**, not existing capabilities.

### What this does and does not prove

- **No success-before-enqueue branch exists in this path.** A known refused insert, unavailable manager, full queue, or rejected database query cannot produce the normal 202. CDP replies 500 and Django exposes 503 `delivery_unavailable`. The queue-depth lookup itself fails open on lookup error, but the actual insert must still resolve. [M-queue] [M-insert] [M-depth] [F-service]
- **A timeout is an unknown outcome.** For example, Postgres commits, CDP waits in a subsequent monitoring flush, Django times out, and the SDK sees unavailable or a transport timeout. The worker may still send. The same uncertainty exists if the insert commits but its database acknowledgement is lost. There is no compensating removal of an accepted job. [F-client] [F-cdp] [M-insert]
- Monitoring flushes normally swallow broker failures. They can still consume response time; an unexpected exception after insert also sits inside CDP's 500 catch. They are not an atomic second acceptance record. [M-monitoring] [M-terminal]
- A malformed CDP 202 body can also produce a Django server error: parsing `response.json()['invocation_id']` is outside the service's HTTP-exception handler. A malformed external success body is separately an SDK error. [F-service] [N-send]
- “Durable” here means **acknowledged persistent Postgres queue insertion**, subject to the database's durability/replication configuration. This investigation did not inspect deployed WAL/fsync settings, failover policy, backups or infrastructure failure behavior. Source code alone cannot prove survival of every storage failure.
- The queued item is a **workflow invocation and variables**, not an immutable rendered MIME message. `functionId` reloads the current flow; `flowVersion` is attribution, not a snapshot lookup key. A template/workflow edit can affect an accepted send before execution. [M-id] [M-load]

There are three acknowledgements to keep separate: PostHog queued it; SES accepted a `SendEmailCommand` and returned a `MessageId`; a later provider Delivery event reported recipient-server acceptance. None is a promise of inbox placement or reading. The route only waits for the first. [M-ses] [M-feedback-map]

### Retry exhaustion is not one mechanism

1. Ordinary non-throttle send errors finish failed at the application layer after the AWS client's behavior, rather than entering a universal application retry loop. [M-email-result] [M-ses-client]
2. SES throttling and local pacing reschedule without an application deadline/max-attempt branch in the inspected email service. A stuck pending send needs a deadline/age signal if the product wants every accepted request to reach a terminal outcome. [M-pacing] [M-email-result]
3. Crash/stall retries belong to Cyclotron's janitor, with a configurable touch budget and poison-pill handling. This is not an SES delivery retry counter. Durable poison recording is a stronger path than ordinary monitoring; if recording fails, it retains the job instead of silently deleting it. [M-janitor] [M-durable-failure]

### Why the current signals are not a developer guarantee

- Worker `runBackgroundTasks` first settles the Postgres job (`fail`, `cancel`, `ack`, or reschedule), **then** publishes normal monitoring/results. The comment explicitly avoids replaying sends just because monitoring failed. A crash between these operations can lose the terminal signal without replaying the finished job. [M-worker-flush] [M-settle]
- Invocation results are optionally disabled by `HOG_INVOCATION_RESULTS_ENABLED`. Normal lifecycle `flush` drains its buffer, catches output errors and does not restore/retry the lost rows there. Captured person events similarly drain and catch errors. Logs/metrics are best-effort too. Operator logs/metrics are not delivery to the API caller. [M-terminal] [M-results-flag] [M-capture] [M-monitoring]
- Lifecycle is `running`, `succeeded`, `failed`, `canceled`, based on execution error/cancel state, not email delivery. A later bounce does not change that status. Suppression and policy skips may thus read as success. [M-terminal] [M-feedback]
- Engagement capture requires `shouldCaptureEngagementEvents`; defaulting distinct ID to the recipient address does not enable capture. Sent/failed and SES-feedback person events identify workflow/action/recipient/subject, but **omit invocation/message ID**, making repeated sends to the same person difficult to correlate. The tracking path internally knows the invocation ID for logs. [F-service] [M-email-result] [M-feedback-events] [M-person-capture]

Missing/unparseable tracking attribution is dropped with an operator counter/log, not a send-specific developer failure. Run-log publication and suppression-update failures in the webhook handler are caught and do not force its response to fail. A successful webhook response is therefore not an end-to-end notification receipt. [M-feedback] [M-feedback-handler]

### Existing status lookup, with important limits

There is already `GET /api/projects/{id}/hog_flows/{workflow_id}/invocation_results/{invocation_id}/` (and list/count endpoints). It reads latest lifecycle data from ClickHouse, returns a result with status/error details or 404, and requires workflow/person read access. Do not assume the same send-only PSAK can read it: `HogFlowViewSet` does not add the send route's PSAK authenticator/action allowlist, and a send-only scope lacks `person:read`. The send response supplies only the invocation as `message_id`, not a ready-made email-status URL/workflow ID; the email SDK has no wrapper. This is a useful debugging surface, **not a durable per-email outcome API**: rows are eventually published, can be lost, have a 30-day table TTL, and successful execution can mean skipped delivery. [M-lookup] [M-lookup-scopes] [M-lookup-view] [M-result-schema] [M-result-ttl] [M-terminal]

## 4. Idempotency

**No send-request dedupe today.** Every admitted request calls `createHogFlowInvocation`, which generates a new UUID. Queue conflict handling concerns explicit reruns of an existing invocation, not repeated API requests. `distinctId` is attribution; a template content hash is content coordination. Neither identifies a send operation. N provides no idempotency-key parameter/header. [M-id] [M-insert] [N-body] [N-transport]

A minimal client-key design would need:

1. SDK `idempotencyKey` passed to Django and CDP; scope it to project plus send operation, not a process or secret key. Rotating an API key should not bypass an existing send's identity.
2. Durable unique `(team_id, idempotency_key)` ownership, a canonical request fingerprint, the stable message ID and acceptance result. Same key/same request returns the first result; same key/different request returns a conflict. Define canonicalization and template-reference/version semantics explicitly.
3. Atomically create the receipt **and** the queue job. The natural queue-side seam is Cyclotron Postgres beside `bulkCreateJobs`, with a database uniqueness constraint/transaction, not a check-then-insert Redis lock. If a receipt lives in Django's different database, use an outbox/reconciliation design; two independent writes are not atomic.
4. Handle simultaneous requests and “insert committed, response lost” by reading the same receipt. Retain it after the queue job completes/deletes, for a documented retry window. Validate/scoped-authorize every request, but an already-accepted same-key retry should return that acceptance rather than rerunning mutable admission checks and pretending nothing was accepted.
5. Only enable automatic SDK retries once they reuse the same key and server contract, including ambiguous 5xx/timeouts. Status/readback by key must let a client recover a lost first acknowledgement.

This deduplicates **API admission**. It does not make the external SES side effect atomic with Postgres. `SendEmailCommand` receives no invocation-id dedupe token here; a worker crash/unknown provider outcome still needs an explicit duplicate-risk policy. Exactly-once inbox delivery is not a promise these changes can make. [M-ses] [M-worker-flush]

`send()` is a result-returning API: ordinary failures are **not thrown to the caller**. A developer who only catches exceptions and never checks `result.error` can miss a refusal. ## 6. Smallest change seams

These are suggested slices for the parity spec, not implementation performed by this research.

### A. Preserve the existing acceptance boundary

**No queue migration or new enqueue stage is required to make “success implies an acknowledged persistent enqueue” true.** Keep 202, await the existing insert, and describe it precisely. Do not change to 200 just to match the ticket's wording.

Small acceptance-contract changes:

- `products/messaging/backend/facade/contracts.py`: remove the unconditional “Safe to retry” claim from `DeliveryUnavailable`.
- `products/messaging/backend/presentation/views/transactional_email_api.py` and `messaging_send.py`: say unavailable can mean acceptance unconfirmed, and distinguish accepted-for-processing from provider delivery.
- `nodejs/src/cdp/cdp-api.ts`: keep queue insertion as the only acceptance prerequisite; make telemetry explicitly non-fatal/non-gating after acceptance so telemetry does not unnecessarily prolong the response. This reduces false negatives but cannot eliminate lost HTTP responses.
- `nodejs/src/cdp/cdp-api.serial.test.ts` and the queue-adapter tests: assert response remains pending while insert is pending, insert rejection refuses, and telemetry failure cannot turn acknowledged insertion into a false “nothing queued” result. Existing Python API tests mock a CDP 202, so they do not alone prove durability. [F-tests-send]
- Existing transactional-email docs and N's `packages/node/src/emails.ts` API description: state the acceptance/unknown-error contract. Update behavior docs in their existing repository/page, not a new product doc in this report branch.

Add synchronous sender/suspension/suppression/render preflight only if the spec wants **“currently eligible for delivery”** as well as queued. Reuse worker services, rather than independently implementing Liquid/policy in Python. Keep execution checks for changes after admission. Persist an immutable send payload/version if the preflight result must describe exactly what later sends.

### B. Make ambiguous retries recoverable

Implement the durable idempotency receipt alongside queue insertion as described above. Touch:

- `messaging_send.py` and `transactional_email_api.py`: input/response schema.
- `products/messaging/backend/services/transactional_email.py` and `posthog/plugins/plugin_server_api.py`: forward key/fingerprint and preserve the accepted ID.
- `nodejs/src/cdp/cdp-api.ts`, `services/job-queue/job-queue-postgres-v2.ts`, `services/cyclotron-v2/manager.ts` plus a queue-database migration: atomic receipt/job creation and replay of prior acceptance.
- N `packages/node/src/emails.ts`, `packages/node/src/client.ts`: caller option, propagation and same-key retry policy/tests.

A queue-only UUID collision check or short-lived Redis marker is insufficient because completed jobs and lost acknowledgements must remain recoverable.

### C. Smallest usable later-failure surface: lookup by returned ID

There are two levels; do not confuse them:

1. **Cheapest partial improvement:** expose an email-friendly wrapper around existing invocation lookup and return enough identifiers/a status URL; add N `emails.get(id)`. It would help diagnose failed/canceled runs, but retains the skip, Kafka-loss, late-provider-feedback and retention limitations above. It must not be sold as “every later failure”.
2. **Smallest surface that can support the stated guarantee:** a durable, project-scoped email receipt/status record keyed by `message_id`, updated with explicit no-send reasons **before job settlement**, plus provider outcomes from feedback. Poll that record by ID. Keep execution state separate from provider delivery state, expose waiting/attempt/age information, and distinguish `skipped`/`canceled`/`failed` from `accepted_by_provider`/`delivered`/`bounced`. If a provider outcome is unknown, report unknown; do not manufacture a failure or success.

The narrow endpoint can live in `products/messaging/backend/presentation/views/messaging_send.py` with a service/facade behind it and registration in `products/messaging/backend/routes.py`. Durable receipt storage must share the queue transaction or use an explicit outbox; do not add a Django receipt write next to queue insertion and claim atomicity. Worker seams are:

- `nodejs/src/cdp/consumers/cdp-cyclotron-worker-hogflow.consumer.ts`: missing-flow/team and cancellation terminal outcomes.
- `nodejs/src/cdp/services/hogflows/actions/hog_function.ts`: render/preference/address-validation outcomes before email service entry.
- `nodejs/src/cdp/services/messaging/email.service.ts`: sender/policy/suppression/wait/SES outcome, stable reason and provider MessageId.
- `nodejs/src/cdp/services/job-queue/job-queue-postgres-v2.ts`, `services/cyclotron-v2/manager.ts`, `consumers/cdp-cyclotron-worker.consumer.ts`: persist outcome atomically with queue settlement, or durably outbox it; do not make telemetry failure replay a send.
- `nodejs/src/cdp/services/cyclotron-v2/janitor.ts`: durable crash-exhaustion/unknown outcome.
- `nodejs/src/cdp/services/messaging/helpers/ses.ts` and `email-tracking.service.ts`: provider outcome updates, DeliveryDelay, correlation and feedback dedupe.
- N `packages/node/src/emails.ts` / `client.ts`: lookup method and typed outcome.

A read API is smaller than reliable outbound webhooks. It gives a developer a way to learn about later failures, provided they poll/reconcile and the product defines retention and deadline behavior. It cannot guarantee knowledge of outcomes SES itself never reports. A long-wait/unknown state is necessary for missing feedback or indefinitely unavailable delivery.

### D. Events or webhook alternatives

**Events:** add `$email_message_id` (the invocation ID) and stable reason/error fields to existing sent/failed/provider events; emit explicit no-send outcomes for policy/suppression/render/load/cancel paths too. Relevant files are the three execution/worker files above plus `email-tracking.service.ts`. Opt-in best-effort analytics events alone remain insufficient. Publish from a durable outbox/receipt if notifications must be recoverable, and do not expose whole message data in generic error events.

**Webhook:** useful push UX, but not the smallest first surface and currently outside the map's stated scope. Build it on the same durable outcome/outbox, with authenticated endpoint ownership, signing, retry/backoff, stable event IDs, dedupe, replay/retention and exhausted-delivery visibility. The SDK's original send result cannot be retroactively changed. The receipt/status contract should be the source of truth; webhook delivery is another asynchronous delivery problem.

### Spec decisions this research unblocks

The existing parity-spec ticket can now choose, without another implementation survey:

- Preserve “accepted for asynchronous processing”, or synchronously require current render/sender/policy eligibility too?
- Allow mutable linked workflow content for already-accepted sends, or pin the exact send payload?
- Require an idempotency key for recoverable retries, or document duplicate risk?
- Is opt-in analytics sufficient, or is durable status by message ID required?
- Which waiting deadline applies to time-critical transactional sends, and how are unknown provider outcomes reported?

No new implementation was started, no broad test/build/stack was run, and no production delivery or infrastructure proof is claimed.
