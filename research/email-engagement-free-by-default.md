# Email engagement: free analytics events, scoped default-on capture

## Answer

**Yes, technically.** PostHog can retain email engagement as normal, person-linked analytics events while excluding it from Product Analytics event usage. Capture can default on for sends from code without changing `capture_workflows_engagement_events` for existing workflows. This needs a billing decision and coordinated rollout, not just a new SDK default.

**Recommended proposal:** exempt the exact existing email event names for all email sends; default capture on only for the code-send contract. These are separate scopes. The broad named exemption fits the current billing architecture and avoids inventing a trusted-origin billing protocol. Existing workflow capture remains opt-in, even though its captured email events would become free too.

If Billing approves **only code-send events** as free, the implementation is larger: establish trusted send provenance through capture, ingestion, stored events and both usage-counting paths. A customer event property is not enough. Do not ship a property-based approximation.

Here, **free means no Product Analytics event, enhanced-person-event or group-event usage from these events**. Email delivery, other workflow execution and independently metered products remain unchanged. It does not mean unlimited storage, queries or delivery, or an exemption from operational limits.

This is a researched recommendation, **not an approved billing policy**. The exemption is a proposed amendment to grilling's “no pricing or tier code” boundary. Make free-by-default capture a conditional requirement in the spec; do not represent the approval or downstream billing proof as complete.

### Do the events stay queryable?

**Yes, when successfully captured and retained.** The exemption suppresses usage records, not event creation or person processing. `nodejs/src/ingestion/pipelines/analytics/event-subpipeline.ts:158-183,194-227` still creates and emits the ordinary event after the usage step. The person timeline uses a general `EventsQuery` filtered by person, not billing status (`products/persons/frontend/logics/personsLogic.tsx:72-87`). Settings explicitly advertises insights, funnels and dashboards (`frontend/src/scenes/settings/SettingsMap.tsx:1818-1824`). No special email query engine is needed.

Do not disable person processing as a billing workaround: that weakens the identity promise rather than creating an exemption. Keep the application's canonical distinct ID, normal retention/access/query rules and the prior report's browser/replay limitations. “Queryable” is not a guarantee that a blocked or dropped event arrived.

## Scope and operational limits

### Name-based versus code-send-only exemption

| Choice                                                              | Consequence                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Exact named events free regardless of send origin - recommended** | Fits the current name-only classifier and SQL exclusions. All captured workflow-email events benefit, but capture defaults change only for code sends. This is a broader billing change than the minimum requested; obtain explicit approval.                                                                                                 |
| **Only code-send events free**                                      | Cannot be expressed by today's `UsageKeyResolver(event: string)`. Requires server-established provenance from an accepted code send, propagated through callbacks and capture into ingestion and stored rows. Node and legacy/report queries must agree on verification, absence and compatibility. This is not a small property/filter edit. |

The authenticated send entry can establish that a send came from code; ingestion cannot recover that fact from today's event name alone. The current path queues the transactional workflow and its recipient identity (`nodejs/src/cdp/cdp-api.ts:1150-1197`); the capture envelope then carries event name, distinct ID, timestamp and properties (`nodejs/src/cdp/services/captured-events/captured-events.service.ts:45-56,64-82`). `nodejs/src/common/services/internal-capture.ts:14-29,40-61` is generic transport, not an email-only billing contract.

Do not treat API/SDK attribution, transactional category, a workflow ID, template metadata or `capture_internal` as verified billing eligibility. Attribution answers a product-usage question; pricing provenance answers a different one. Under a code-only policy, any billing eligibility field belongs to server-owned accepted-send state, not caller variables. A callback's signed capture choice alone does not automatically create trusted provenance at the later analytics boundary.

### What existing controls bound - and what they do not

Existing API authentication, scopes and throttles, workflow quota checks and email delivery controls constrain new sends. Source: `products/messaging/backend/presentation/views/message_templates.py:367-400,599-646`; `nodejs/src/cdp/cdp-api.ts:1150-1197`; `nodejs/src/cdp/services/messaging/email.service.ts:390-603`. Preserve those controls and normal event-size/ingestion protections; free analytics must not mean unrestricted sending.

**A send limit does not bound all later engagement.** Repeated opens, link scanners, clicks and provider retries can create more processing without another send. The inspected metric-to-capture path does not establish a per-message semantic engagement ceiling (`nodejs/src/cdp/services/messaging/email-tracking.service.ts:309-342`). Usage-record identity deduplication (`nodejs/src/common/usage-ingestion/usage-record-batch.ts:47-54`) is not deduplication of repeated logical engagement. Production open/click signals come from provider callbacks; local pixel/redirect capture is restricted to development/test (`nodejs/src/cdp/services/messaging/email-tracking.service.ts:557-589`).

Before launch, Workflows and Ingestion need an explicit duplicate/repeated-engagement policy, bounded per-project/message processing, monitoring and a reversible capture rollout. Preserve useful engagement semantics; document any aggregation or dropping rather than silently describing every open as retained. Limit generated payloads to the supported email-event schema, not an arbitrary free analytics channel. A name-only exemption consciously inherits the existing reserved-event-name policy; require Ingestion's agreement rather than claiming the classifier enforces origin or cost bounds.

There is a separate **availability gap**: analytics capture checks the project's global Events quota before scoped checks (`rust/capture/src/v1/quota_limiter_shim.rs:19-42`; capture-mode mapping in `rust/capture/src/quota_limiters.rs:232-236`). Changing the billing lists does not itself exempt email events from that admission check. Prove the configured internal-capture path for an analytics-limited project. Either retain and clearly document that availability boundary or separately approve an appropriately scoped admission change. Do not promise email engagement always arrives merely because its meter is free.

## Smallest scoped default-on change

### Current behavior

The Django field defaults false, and the worker's missing-config fallback is false (`products/workflows/backend/models/team_workflows_config.py:12-19`; `nodejs/src/cdp/services/managers/team-workflows-config.service.ts:29-42,65-71`). Onboarding can save an enabled choice, as the prior report explains; that is not the runtime default.

Sent/failed events and later feedback currently consult the **current project setting** (`nodejs/src/cdp/services/messaging/email.service.ts:721-743`; `nodejs/src/cdp/services/messaging/email-tracking.service.ts:328-342`). Operational metrics precede that gate (`nodejs/src/cdp/services/messaging/email.service.ts:691-719`; `nodejs/src/cdp/services/messaging/email-tracking.service.ts:309-326`). An SDK-only default cannot fix callback capture.

### Proposed contract on the agreed architecture seams

- **Scope by accepted API send, not by having a body.** REST, SDK, stored-template and rendered-body code sends need the same policy. Workflow-editor, batch, scheduled and other legacy sends keep their existing semantics unless explicitly brought into the new code-send contract. A compatibility route that cannot carry the policy remains legacy; skill v0 must explicitly adopt the new contract or report the limitation.
- **Resolve once.** Django's `EmailSendCommand` carries an explicit capture choice into server-stamped `AcceptedSend.tracking`, persisted in typed `state.send` (the `send` field on `HogFlowInvocationContext`). No writes to caller `variables` and no project-wide setting mutation. The current `accountAudience` snapshot is the existing structural precedent (`nodejs/src/cdp/types.ts:446-452`); these named new seams are the accepted architecture direction, not fields already present in M.
- **Default only after free is verified.** Before that gate, the new contract can snapshot today's project default and accept a per-send override. After approval and deployment of the exemption, omitted capture choice on new code sends resolves true. Keep explicit false authoritative, even if the legacy workflow switch is true. Do not reinterpret queued pre-change sends as opted in.
- **Carry the choice to callbacks.** Extend the existing versioned signed provider tracking context; readers support the new and old layouts before writers emit it. The current context already carries recipient identity and sending workflow version (`nodejs/src/cdp/services/messaging/helpers/tracking-code.ts:50-59,78-97,194-214`). New-policy callbacks use the recorded choice even after setting changes or template republishing. Legacy callbacks with no policy retain today's project-setting behavior. A later emergency rollout stop must be explicit, not an accidental fallback to the legacy switch.
- **Keep policies distinct.** Capture controls customer analytics events. Open/click tracking, recipient consent and UTMs remain separate. `captureEngagement: false` alone does not disable tracking. Conversely, tracking off still allows sent/delivery/failure events if capture is on. Current independence is visible at `nodejs/src/cdp/services/messaging/email.service.ts:721-743,898-943`. Preserve the accepted new-code-template UTM choice from the earlier research; do not rewrite existing templates as part of this billing change.
- **Keep other outputs independent.** Workflow metrics, send billing, message assets and the planned operational status service do not depend on optional customer capture. Editor test sends and preview renders remain outside production engagement. Keep `$email_message_id` correlation on the architecture's sent, failed and feedback signals; do not build a new status store or browser identity bridge for this requirement.

**What a team sees:** supported email events alongside its recipient's product events, with no additional analytics-event usage for the exempt set. This requires the same stable application ID; explicit email-only mode is weaker attribution, not an automatic person lookup. Existing workflow capture does not turn on behind the team's back. The team can pass `captureEngagement: false` on its sends; its application can set that consistently as a code default without requiring a new project setting in the smallest slice. To stop open/click collection too, it needs the independent tracking-off option. Settings/docs must explain the distinction and stop saying the exempt set is billed as ordinary events (`frontend/src/scenes/settings/SettingsMap.tsx:1822`).

This adds events that can affect event-triggered behavior as well as dashboards. Disclose and test that boundary, including preventing unintended workflow feedback loops. Free is not the same as consequence-free.

## What the architecture prototype must show

[Shape the architecture of Resend parity](https://github.com/Silthus/posthog/issues/526) already has the right seams. Extend its diagrams/contracts and synthetic proof plan; do not reopen HogFlow, mutable variables or the status-store decision.

- **One policy path:** REST/SDK → `EmailSendCommand` → server-stamped `AcceptedSend.tracking` in `state.send` → worker sent/failed capture → versioned provider context → callback capture. Include stored-template code sends, not just body sends. Show where legacy sends branch back to today's setting.
- **One billing choice:** for the recommended named exemption, mark the exact shared event set at Node and Python, with no caller-supplied billing field. If owners instead choose code-only, show the complete trusted-origin path and both classifiers; a mark only on the command/header is incomplete.
- **Separate outputs:** recipient events remain queryable; operational metrics/status and API attribution still work when capture is false; the email-send meter is unchanged. Show message and canonical person correlation without fabricating a browser session.
- **Compatibility/default matrix:** project capture off/on; absent/true/false send choice; legacy/new queue state and tracking context; delayed callbacks after setting/template/default changes; tracked/untracked message; explicit user/email-only identity; test/preview sends. Before the billing gate, absence preserves the existing default; afterwards it defaults on only in code scope.
- **Metering proof:** ingest synthetic examples of every exempt event plus a normal custom event. Check retained events, no exempt event/person usage records, legacy ordinary/person/group exclusions, counter comparisons, quota/report handoff and Billing's downstream fixture. Keep delivery usage unchanged. Source code reading alone does not prove invoices.
- **Failure/bounds proof:** replayed requests keep the accepted policy; duplicate provider feedback and repeated engagement follow the documented policy; capture failures do not retry an already-sent email; an analytics-limited project has the explicitly chosen behavior. Observe unintended event-triggered workflow effects.
- **Production-shaped callback proof:** a synthetic provider send preserves capture choice and recipient/message correlation through real feedback. Maildev pixel/redirect behavior alone is insufficient (`nodejs/src/cdp/services/messaging/email-tracking.service.ts:557-589`). Keep real recipient material and provider credentials out of the public artifact.

**Outstanding evidence:** billing-owner approval and economics; downstream consumer/invoice verification; effective-date/history reconciliation; agreed operational bounds; the configured capture-quota behavior; executable prototype tests and a synthetic production-shaped callback run. This report proves source-level feasibility and identifies the required work; it does not claim those launch proofs have happened.
