# How other tools model parallel paths and joins

Research for Silthus/posthog#496, child of the map in #493.
Question: how do n8n, Zapier Paths, Make routers, Customer.io, Braze, AWS Step Functions `Parallel` and Temporal model parallel paths and joins?
Method: vendor documentation only.
Where a page did not answer a question, the table says "not found" instead of guessing.
Read on 2026-10-16.

## Headline

Only two of the seven tools run paths concurrently with a built-in wait-for-all join: AWS Step Functions `Parallel` and Temporal (`Promise.all` and equivalents).
The four automation and journey tools run a routed set of paths one at a time, or send each person down exactly one path.
n8n runs branches one after another, and Zapier and Make say so explicitly.
Customer.io and Braze use first-match routing, so a person takes one path.
Zapier Paths and Make routers cannot rejoin.
Customer.io, Braze and Make rejoin only exclusive branches, which is the out-of-scope case on the map.

## Cross-cutting findings

1. **Real concurrency is rare in the visual tools.** n8n, Zapier and Make document sequential execution. Their "parallel" paths are really "all matching paths, in order". Users who need real parallelism leave the tool (Sub-Zap, sub-workflow, Step Functions).
2. **Rejoin is the weak spot of the router family.** Zapier Paths and Make routers cannot rejoin. Make rejoins only If-else routes, with a dedicated Merge module that pairs each rejoin with its split. That is the structured pairing our block uses.
3. **Code-first engines expose the join as a choice of combinator.** Temporal makes "all", "allSettled" and "race" a coding decision. Step Functions fixes it to "all" with fail-fast. Our v1 (`allSettled` plus a continue / stop setting) matches Temporal's recommended partial-results pattern.
4. **Fail-fast is the default in both concurrent engines.** Step Functions stops the other branches, and Temporal's `Promise.all` rejects on the first error. Neither guarantees that in-flight external work stops: Lambda keeps running, and a Temporal activity needs heartbeats to see a cancel. This supports leaving cancellation out of v1.
5. **Results are positional in the engines and merged-by-mode in n8n.** Step Functions returns an array in branch order. Temporal returns whatever the code builds. n8n offers many merge modes. None offers a status-plus-output record per named path, so our namespaced per-path result is a deliberate improvement. Position-only results break when a branch is reordered.
6. **Size limits bite at the join.** Step Functions: 256 KiB per state input or output. Temporal: 2 MB per payload. n8n: 100 MB display cap, no hard data cap found. A join that gathers N path outputs multiplies output size by N.
7. **Concurrency needs a throttle.** Temporal's docs advise `maxParallel` batching and warn at 500 or more pending activities. Zapier caps paths at 10, Customer.io at 20, Braze Audience Paths at 8. Our 2 to 5 range with the `max_parallel_tasks` warning is tighter than all of these.
8. **Run history shows the paths, not the concurrency.** Zapier and Make list steps and bundles. Step Functions draws a graph. Temporal shows an event list. The sources do not show a view that reads as "three lanes, one waiting". Whether any tool does is uncertain.

## Implications for our structured parallel step with a wait-for-all join

- **Our v1 is already ahead of the visual tools.** n8n, Zapier and Make run paths sequentially. Real concurrency with a paired join puts us nearer to Step Functions `Parallel` and a Temporal `allSettled`. The editor can still draw it like a router.
- **Keep the split and join as a pair.** The only tool with a safe rejoin (Make If-else plus Merge) pairs them. The unpaired designs (Zapier, Make routers) cannot rejoin at all. This confirms the `Promise.all` framing.
- **Return a named record per path, not an array.** Step Functions' positional array is the cautionary tale. Expose `{ status, output }` keyed by a stable path id, in addition to the per-path output variables already decided.
- **Fail-fast is not free, so skipping it for v1 is defensible.** Both engines that implement it leave in-flight external work running. For AI task steps, a "stop" decision at the join will still have paid for every path. Say so in the join's settings copy.
- **Budget join output size explicitly.** Step Functions' 256 KiB and Temporal's 2 MB show that gathering N outputs hits a payload ceiling. Define a cap per path result and a total for the namespaced join result, and fail the path or truncate predictably instead of failing the whole run.
- **Treat concurrency as a throttled resource.** Temporal's batching guidance and the other tools' small path caps match the 2 to 5 decision. The save-time warning against `max_parallel_tasks` is the right place, because a runtime queue would make a path look hung.
- **Make the run view show lanes and the wait.** No tool surveyed has a clear lane-and-wait view. The run view needs per-path status and a visible "waiting for N paths" state at the join. This is a differentiator and a risk, since the sources give no pattern to copy.
- **Duplicate-write detection at save time stays valuable.** Source tools avoid the problem (positional results, sequential execution, explicit merge modes). Concurrent writes to one variable are a new hazard for us, so the save-time check from the decisions belongs in v1.
