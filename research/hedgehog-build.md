# Can hedgehog mode play a scripted workflow build?

**Answer:** Yes, after focused changes to the upstream package. It already supplies customized sprites, jump and position primitives, animation callbacks, and multiple actors. It does not supply a scoped, deterministic, cancellable build player. Mounting the current game inside the canvas is insufficient.

Research for [ticket #436](https://github.com/Silthus/posthog/issues/436) and [map #435](https://github.com/Silthus/posthog/issues/435), including the map's Notes. Read on 2026-10-12. This is a research artifact, not an implementation or a PR.

**Executed proof:** Mounting `.62` in a 700×440 element at client `(101, 81)` produced a 1280×800 game screen. A React Flow node initially 160px wide retained a 160px collider after zooming to 0.5, when its DOM width became 80px. The collider center followed the pan/zoom translation. React Flow's `flowToScreenPosition({x:70,y:40})` returned the same client point as the node rectangle. Adding and removing a controlled React Flow node changed the platform count from 10 to 11 to 10.

### Where the renderer fits in the workflow editor

`HogFlowEditor.tsx:50-70` already owns the React Flow instance, wrapper ref, node-ready signal, and resize handling. Put the scoped animation over the **inner canvas wrapper**, not the outer editor that also contains `HogFlowEditorPanel`. The wrapper at lines 84-130 is the integration seam. The editor already receives viewport changes, but currently dispatches only when its detail threshold changes. [W1]

ELK lays out downward, anchors the trigger at `(0,0)`, and returns graph-space positions and fixed node dimensions. The constants are width 120, height 34, and zoom range 0.1 to 2. Node centers and top surfaces can therefore come from the finished graph, without scanning every DOM node. `SmartEdge.tsx` derives edge geometry separately; there is no existing animation timeline there. [W2, W3]

Two viable coordinate strategies:

1. **Prefer graph-space playback.** Render actors and persistent flags in React Flow's viewport coordinate system, using a package renderer that accepts graph-space positions. `ViewportPortal` is the existing React Flow facility for content that follows pan and zoom. Do not place the current window-coordinate game inside it: that applies the viewport transform to already transformed client coordinates. [X1, S1, S5]
2. **Use a canvas-local pixel overlay.** Convert each graph point with `flowToScreenPosition`, then subtract the wrapper's client origin. Apply zoom to actor size and path geometry. A package container option must make viewport, platform, and input calculations use the same local origin. [X2, W1, S3]

The map's user pan/scroll/key interruption rule avoids following manual camera movement mid-sequence. Its automatic downward camera motion for tall graphs still needs the adapter. Fit the final graph before the sequence; wait for node initialization and completed layout. Coordinate with existing `fitView`, which reacts to selection and wrapper size and accounts for the side panel. Animation time must not write graph positions or race that camera logic. [W1, W4]

Recommendation: use finished-graph positions for a scripted mode, retain explanation flags as accessible host UI in the viewport, and leave their hover/click behavior in Workflows. The package owns the mascot's movement and art. This recommendation follows the map's fixed-graph replay and persistent-flag requirements.

**Executed proof:** Spawned four actors, removed one directly, and observed three remaining. On a grounded default actor with no held flag, a non-looping `wave` called `onComplete`. A grounded `jump()` immediately set velocity to `{x:0,y:-15}`. A wave requested in the air was replaced with `fall`; its callback had not fired after 80 ms. `game.destroy()` marked the instance destroyed. Complete listener cleanup was read from source, not established by that last check.

## PostHog loading and the user's hedgehog

- The web app uses `lazyWithRetry` and `Suspense` to import `HedgehogModeRenderer` only in a browser. It passes `state.options = hedgehogConfig.actor_options`, a platform selector, theme, and `onGameReady`. Its normal mode is fixed over the whole app at z-index 999998. Reuse the lazy loading and assets helper, but use a separate scoped playback instance. Do not register the playback game as the global roaming game. [P2]
- `getHedgehogModeAssetsUrl()` chooses `/static/hedgehog-mode`, prefixes the toolbar UI host when needed, and otherwise uses the current origin outside localhost. `frontend/build.mjs:35-38` copies installed `assets/` into the built `hedgehog-mode` directory. SpritesManager loads `sprites.png` and uses the package's matching JSON atlas. Update package and assets together. [P2, P3, S19]
- `hedgehogModeLogic` seeds from `userLogic.user.hedgehog_config` after mount, otherwise loads `/api/users/@me/hedgehog_config`. `hedgehogConfig` sanitizes that remote config. The version-1 migration supplies actor options; version 2 passes through. This selector, not the enabled flag, is the source for the person's appearance. [P4, P5]
- Settings lazy-load customization and write `actor_options` through `updateRemoteConfig`. The normal roaming game is synchronized through `stateManager.setHedgehog`; changes in its state are checked each second. For build playback, copy appearance (`skin`, `color`, `accessories`, `flag`) into actors with fresh IDs and scripted behavior overrides. Do not persist temporary clones, movement state, or disabled AI back to the user's configuration. `onStateChange` can let the playback host own persistence without writing the roaming game's localStorage key. [P4, P6, S20]
- Static profile rendering already lazy-loads `StaticHedgehog` using the same asset URL and actor options. It renders a single frame and does not supply an animated actor/action API. [P7, T7]
- Desktop Code's `RendererHedgehogModeHost` lazy-imports the package, calls `new HedgeHogMode({assetsUrl:'./hedgehog-mode', state:{options:actorOptions}})`, renders into its supplied container, and returns a destroy/context-health handle. Shared desktop UI gets appearance from `user.hedgehog_config.actor_options`, mounts the host, and tears it down on cleanup. The web desktop host is a no-op. Mobilehog uses copied walk/idle sprite strips with React Native animation rather than hosting this engine. [D2, D3, D4]

**Appearance caveat:** `.62` checks for a skin's idle animation to decide whether it exists. Spiderhog, robohog, and hogzilla lack that animation and fall back to the default body. `.63` fixes detection and repaints after customization updates. Start the package work from `.63` or include that fix; do not judge custom-skin support solely by a `.62` preview. Ghost has only idle frames, so new action playback also needs an explicit per-skin fallback rule that preserves the chosen appearance. [S10, R2, A1]

## Reduced motion and frame cost

**Reduced motion: missing in the game.** Source/config searches found no `prefers-reduced-motion` handling or game-level reduced-motion setting. The map already specifies the right host behavior: fade nodes top-down and do not mount a hedgehog or physics engine. React UI text-animation options are not a game motion preference. [T1, T7]

**Synthetic browser probe, executed:** Installed `.62` was bundled with the checkout's esbuild into `/tmp/hedgehog-build-probe/`. It hosted React Flow **12.6.0** with ten invented nodes. T3's Chromium **154** preview ran at 1280×800 and device-pixel ratio 2. No product-path experiment files were committed. After checking the incorrect smaller-container geometry, the actor tests used a window-origin overlay to avoid conflating coordinate error with animation behavior.

For each actor count, 180 requestAnimationFrame intervals were collected. Engine timing started at the first `beforeUpdate` listener and ended after existing `afterUpdate` listeners, including the package's element updates and render submission. These are local synthetic measurements, not production or internal product metrics.

| Configuration                          | Engine steps | Mean engine step | P95 engine step | Median rAF interval | P95 rAF interval |
| -------------------------------------- | ------------ | ---------------- | --------------- | ------------------- | ---------------- |
| 1 actor, 10 platforms                  | 288          | 0.10 ms          | 0.20 ms         | 33.2 ms             | 33.4 ms          |
| 4 actors, 10 platforms                 | 301          | 0.16 ms          | 0.30 ms         | 33.3 ms             | 33.4 ms          |
| After game destruction, canvas remains | not measured | not measured     | not measured    | 16.7 ms             | 16.7 ms          |

The CPU samples are low, but the preview's frame cadence changed from about 60 Hz without the game to about 30 Hz with it. This does **not** establish the cause or a real-editor frame budget. Browser diagnostics included GPU ReadPixels stall warnings. GPU execution, composition, full-editor React work, large graphs, and other machines were not measured. A handful of actors is feasible in this probe, but claiming 60 fps would be unsupported.

Source explains where to trim work: every physics step updates all elements and renders Pixi; every platform reads its DOM rectangle even when unchanged; discovery scans periodically; a Matter debug renderer runs even at zero opacity; each web adds eight simulated rope links. Scripted graph positions avoid platform scans, and an opt-in debug renderer plus one coordinated render loop deserve validation in the prototype. Bound concurrent clones and stop playback immediately on Skip. [S1, S4, S5, S16]

## Source ownership, release, and package work

The package's `repository` field identifies **PostHog/hedgehog-mode**. The package metadata lists **Ben White** as author. No checked-in CODEOWNERS/owners file was found. Author metadata does not establish the current reviewer or release approver. [R1]

The source README documents the library, playground, and `texturepacker` asset tooling. There is **no library changelog** in this checkout. The available `hedgehog-mode-anywhere/CHANGELOG.md` belongs to the browser extension; it was read but is not the library's release history. GitHub's releases API returned no releases. Use source commits, package versions, and registry `gitHead` for the baseline. [R3, R4]

Release path: land package code, source art/atlas, tests, and a package-version bump in that repository. Its `cd.yml` runs on pushes to `main`, checks for a new package version, builds `hedgehog-mode`, and publishes the public package. PostHog then advances its frontend dependency/lockfile and recopies the assets during build. A caret range alone does not update the committed lockfile. Desktop requires a separate nested-lockfile update if it should consume the release too. No release was attempted here. [R5, P1, P3, D1]

The map's **“Changes to @posthog/hedgehog-mode” fog is now specifiable**:

1. **Scoped playback surface:** explicit container dimensions/origin or graph-coordinate adapter, correct resize/zoom behavior, and full lifecycle cleanup. Decide whether scripted mode needs physics at all; finished graph positions can define standable surfaces directly. [S1-S5, W2]
2. **Scripted actor contract:** exact timed path/hop, explicit pose ownership, awaitable completion, cancellation, deterministic spawn placement, immediate clone removal, disabled roaming/input/skin abilities, and supported-action fallback for every skin. These are missing API contracts, not missing physics primitives. [S6-S14]
3. **Core art and effects:** construction pose, rappel pose/rope effect, planting pose and eye-flag prop, and clone poof if the prototype requires it. Keep persistent explanation controls in Workflows. [A1, S16, S17]
4. **Delighter art:** backpack plus throw, rocket plus ride/launch, tent plus nap, and tool props plus work poses. Add them to package-owned sprite tooling and atlas, not a PostHog-local fork. [A1, R3]
5. **Performance proof:** one coordinated render loop, debug drawing off by default, no whole-page discovery in playback, bounded clones, and an isolated/full-editor comparison at supported zooms. Host reduced-motion detection must avoid mounting the engine. [S1, S4, S5]

The map's slice 1 can proceed without these changes: node reveal, persistent flags, replay, autoplay hooks, and reduced-motion behavior. Package work is a dependency for slice 2's mascot choreography and slice 3's extra art.

## Verification boundary and remaining unknowns

**Run:** installed `.62` rendering over isolated React Flow; mount geometry; pan/zoom position versus width; node appearance/removal; four actors; direct actor removal; grounded wave callback; jump velocity; airborne pose override; synthetic engine/rAF timings; destruction state. Preparation and all Node/package commands ran from the separate PostHog worktree through `.codex/with-flox`. Package registry metadata was fetched with `pnpm view`.

**Read:** declarations, emitted source maps, complete atlas, package source/README/extension changelog/release workflow, PostHog web loading/settings/config, desktop hosts/mobile sprite usage, workflow editor/layout/edge utilities, and React Flow declarations/implementation. No full PostHog or desktop UI was launched. No new sprites or scripting API were implemented.

**Not established:** real workflow-editor/GPU frame budget; current package review/release approver; art effort and complete per-skin behavior for new poses; physically carrying an actor on a moving platform; full listener cleanup under repeated mounts; feasibility of the final ten-second choreography for very large graphs. These require the prototype or package implementation. They do not prevent specifying the package work above.
