## Short answer

**The Wizard already has most of the machine. It has no email-vendor flow, and its one migration flow is analytics-shaped.**

1. `npx @posthog/wizard migrate <vendor>` is the natural entry. A `wizard migrate` command and a context-mill `migrate` skill with a Statsig variant exist today. Both are flat, and both assume an analytics vendor. Resend is the second vendor, so the repo's own convention says: turn `migrate` into a family.
2. A Resend run is mostly a **skill**, not Wizard code. The Wizard downloads a context-mill skill, hands it to an agent that has file tools, the PostHog MCP and the `wizard_ask` modal, and stops at a local diff plus a report file. It never commits or opens a PR.
3. The run cannot be end to end hands-free. Three steps must go to the person: publishing DNS records, creating the `phs_` key, and any call site that uses a feature PostHog does not have. The Wizard's OAuth login cannot mint a `phs_` key (it needs `project:write` plus a time-sensitive-action check, and the Wizard has neither). The secret-prompt tool exists for exactly this hand-off.
4. **One context-mill skill can serve all three audiences** (Wizard, coding agents, MCP `learn`) if the procedure lives in plain reference files and the Wizard-only conventions (`wizard_ask`, `[STATUS]`, `[ABORT]`, the task pane) sit in a thin, optional section. `send-transactional-email` stays the "how to send" skill; the migration skill links to it and does not copy it.
5. How hard the run is depends on one open decision: **inline content on the send** ([#525](https://github.com/Silthus/posthog/issues/525), [#528](https://github.com/Silthus/posthog/issues/528)). With inline `html`/`react`, most Resend call sites are one-line rewrites. Template-only, every `html:` and `react:` call site becomes a template conversion.

**Smallest first PRs** (details in "Recommended shape"):

| Repo                   | First PR                                                                                                       | Wizard release needed |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------- |
| `PostHog/context-mill` | Add a `migrate-email` skill group with a `resend` variant, `role: skill`. Runs today as `wizard skill <id>`.   | No                    |

| `PostHog/posthog-js`   | None for the run. It waits on the release of #5312 and on the inline-content decision.                         | n/a                   |

## 1. The Wizard today

### Which agent, and where its prompts and skills come from

- **Harness and model.** New programs should use the Pi harness and the orchestrator sequence ([`AGENTS.md`, "Agent execution policy"](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/AGENTS.md)). A program with no `binding` runs on `DEFAULT_BINDING`: Pi, linear, a GPT model at medium effort ([`switchboard/index.ts:101-106`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/agent/runner/switchboard/index.ts#L101-L106)). The Anthropic Agent SDK stays as a legacy fallback. All model calls go through PostHog's LLM gateway.
- **Skills.** The Wizard fetches `skill-menu.json` from the latest context-mill release ([`constants.ts:214-228`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/shared/constants.ts#L214-L228); `getSkillsBaseUrl()` returns the GitHub release URL, or `localhost:8765` with `--local-context-mill`). The menu lists skills by category and a `cliEntries` list of commands ([`skill-menu.ts:21-50`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/shared/skill-menu.ts#L21-L50)). The skill zip is unpacked into the project, scanned by the warlock YARA engine, and removed if the scan flags it ([`skill-install.ts:102-139`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/shared/skill-install.ts#L102-L139)).
- **Prompts.** Product knowledge stays out of the Wizard: "product knowledge never enters infrastructure code" ([`AGENTS.md`, "Design discipline"](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/AGENTS.md)). A native program supplies a short `customPrompt` and points at the skill. The skill's `SKILL.md` does the work.
- **Tools.** The agent gets two MCP servers ([`agent-interface.ts:674-710`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/agent/agent-interface.ts#L674-L710)):
  - the PostHog MCP at `mcp.posthog.com`, called with the run's OAuth token, in CLI mode with a single `exec` tool. The user agent names the running program, so the backend can attribute what the run creates (line 684).
  - `wizard-tools`, in process: env files, package-manager detection, skill loading, and `wizard_ask`.

### Login, keys and env files

- **Login.** OAuth in the browser, once per run ([`login.ts:1-50`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/programs/login.ts#L1-L50)). The base scope list is `WIZARD_OAUTH_SCOPES` ([`constants.ts:268-312`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/shared/constants.ts#L268-L312)): `project:read`, dashboards, insights, notebooks, event definitions and a few Wizard scopes. A program adds scopes with `oauthScopeAdditions`. Two limits from the code comment: the OAuth app has a server-side **scope ceiling**, set in Django admin on both regions, and a scope outside it is silently dropped; and the consent screen lets the person untick scopes.
- **Keys.** The Wizard writes the **public** project token and host. It does not create or write a `phs_` project secret key: a search for `phs_`, `secret_api_key` and `project_secret` in `src/` finds nothing outside tests. The create endpoint is `ProjectSecretAPIKeyViewSet` with `scope_object = "project"` and `TimeSensitiveActionPermission` ([`posthog/api/project_secret_api_key.py:284-289`](https://github.com/PostHog/posthog/blob/17f77e6d1cb/posthog/api/project_secret_api_key.py#L284-L289)). The Wizard has no `project:write` scope.
- **Env files.** The agent calls `check_env_keys` and `set_env_values` ([`posthog-integration/index.ts:441-442`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/programs/posthog-integration/index.ts#L441-L442)). `check_env_keys` returns key names and file paths, never values. `set_env_values` refuses a committed template such as `.env.example` ([`tools.ts:581-600`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/agent/tools/tools.ts#L581-L600)).
- **Secrets from the person.** `wizard_ask` with `sensitive: true` stores the typed value in the Wizard's secret vault and gives the agent a `{ secretRef }`. Only `set_env_values` resolves it ([`tools.ts:116-131`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/agent/tools/tools.ts#L116-L131)). **This is the route for the `phs_` key**: the person creates it in PostHog, pastes it into the Wizard, the Wizard writes it to `.env` and the agent never sees it.

### How it edits code and ends the run

- The agent edits the working tree directly. The Wizard never commits, never opens a PR and never pushes. The Statsig migration skill says so: "Do not commit. The operator reviews the diff and commits when ready" ([`migrate/description.md:65`](https://github.com/PostHog/context-mill/blob/13c9d30/context/skills/migrate/description.md)). The Wizard's own benchmark doc says the same of every run: "only `git diff` is evidence" ([`docs/benchmarking.md`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/docs/benchmarking.md)).
- The run ends with an outro screen that shows a success message and the path of a Markdown report. Generic skill runs write `posthog-<skillId>-report.md` ([`agent-skill/index.ts:20-33`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/programs/agent-skill/index.ts#L20-L33)); the Statsig program writes `migration-report.md` ([`migration/index.ts:5`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/programs/migration/index.ts#L5)). The generic TUI flow is intro, health check, auth, run, outro, "keep skills" ([`skill-flow.ts:13-45`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/tui/programs/shared/skill-flow.ts#L13-L45)).
- A skill talks to the host with text signals: `[STATUS] <phrase>` updates the spinner and `[ABORT] <reason>` stops the run. A native program maps abort text to a friendly message with `abortCases` ([`migration/index.ts:7-17`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/programs/migration/index.ts#L7-L17)). The generic `agent-skill` config has none.

### The migration flow that exists

- `wizard migrate` is a flat command that wraps one native program ([`migrate.ts:7-16`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/cli/commands/migrate.ts#L7-L16)). Its comment reads: "Stays flat while there's only one vendor. When a second vendor lands, restructure into a family … do it explicitly when the second vendor arrives." Context-mill's convention says the same ([`CONTRIBUTING.md:46-57`](https://github.com/PostHog/context-mill/blob/13c9d30/CONTRIBUTING.md#L46-L57)). **Resend is that second vendor.**
- The program is analytics-specific. Its prompt reads "Migrate this project from its existing third-party analytics, feature-flag, and observability tools to PostHog" and it hardcodes `migrate-statsig` ([`migration/index.ts:23-48`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/programs/migration/index.ts#L23-L48)). It sets `disallowedTools: [wizardAsk]` (line 32), although the skill tells the agent to use `wizard_ask` for decisions. The family path avoids this, because it runs the generic `agent-skill` config with the skill id injected ([`dispatch-family.ts:66-80`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/cli/commands/dispatch-family.ts#L66-L80)).
- The skill is a seven-step chain: presence, install PostHog, plan, replace, cleanup, verify, report. A plan file `.posthog-migration-plan.md` carries state ([`migrate/description.md`](https://github.com/PostHog/context-mill/blob/13c9d30/context/skills/migrate/description.md)). Its principles are "replace, do not add" and "make zero unrelated changes". Step 2 installs the **PostHog analytics SDK** by loading an integration skill ([`2-install-posthog.md`](https://github.com/PostHog/context-mill/blob/13c9d30/context/skills/migrate/references/2-install-posthog.md)). That does not fit Resend, which needs `posthog-node` with a secret key. A variant produces its own skill id (`migrate-statsig`), and the variant folder holds the vendor's `sdk-reference.md` and `mapping.md`.

## 3. A Resend run, step by step

**Starting facts**

- `posthog.emails.send` today (#5312 at `87e9e95`): input is `{ template, to, data?, distinctId? }`, with `to: string` and `template` a key or a `templateFile()` ([`emails.ts:33-42`](https://github.com/PostHog/posthog-js/blob/87e9e95ca650a1294d348d9d5023d0772f268782/packages/node/src/emails.ts#L33-L42)). It returns `{ data: { id, warnings }, error }` with `error.code` ([lines 44-70](https://github.com/PostHog/posthog-js/blob/87e9e95ca650a1294d348d9d5023d0772f268782/packages/node/src/emails.ts#L44-L70)). There is no `from`, `subject`, `html`, `react`, `replyTo`, array `to` or idempotency key. The sender comes from the template. The gap list is in [#522 section 5](https://github.com/Silthus/posthog/blob/research/resend-parity-sdk/research-resend-parity-sdk.md).
- The skill steps below follow [#522 section 4, "Steps the skill should run"](https://github.com/Silthus/posthog/blob/research/resend-parity-sdk/research-resend-parity-sdk.md), with the Wizard's tools and limits added.

**Legend**: **Alone** = the agent can do it with the Wizard's tools. **Alone + confirm** = the agent does it after a `wizard_ask` yes/no. **Person** = the Wizard cannot do it; it shows exact instructions and waits.

| #   | Step                                                                                                                                                                                                                                                                               | Who                                                                 | How, and what blocks it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0   | **Detect Resend.** `resend` or `@react-email/*` in `package.json`, `from 'resend'` or `new Resend(` in source.                                                                                                                                                                     | Alone, deterministic                                                | A native `onReady` detector like revenue's (no LLM cost, a clear "no Resend found" before login). ### Scopes

The agent's PostHog MCP token carries only the scopes the Wizard asked for. A Resend run needs more than the base set. The agent-skill program adds only feature-flag scopes ([`agent-skill/scopes.ts`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/programs/agent-skill/scopes.ts)). Needed:

- `integration:read` and `integration:write` for the sender tools (verified in #116863).
- The scope for the template upload tool. Likely `hog_flow:write`, as the by-key routes use it for `phs_` keys. **Not verified** for OAuth tokens.

Two hazards. `oauthScopeAdditions` is per program, so the clean place is a per-family addition, not widening every skill run. And every added scope must be inside the OAuth app's server-side ceiling, which is a Django admin change in both regions; otherwise the token silently lacks it ([`constants.ts:290-303`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/src/shared/constants.ts#L290-L303)). The skill must read the missing-scope case as "use the UI fallback", not as an error.

### Recommendation

**Two skills, one body of reference text. The migration skill is new and does not copy the send skill.**

- `send-transactional-email` stays as it is: it owns "how a PostHog send works", the error codes and the docs reference file.
- A new skill group `migrate-email` with a `resend` variant owns "how to leave Resend". Its steps are the table above. Where it needs sender setup, template upload, or error handling it **points to the send skill's reference file** (a context-mill `shared_docs`/reference link) instead of repeating it. Two copies would drift the first time an error code changes.
- Why a new group, not a second variant of `migrate`. The Statsig chain is analytics-shaped (step 2 installs the analytics SDK, "replace, do not add" forbids new files). Resend needs new files (templates), a sender, a key and hand-offs. Editing the shared chain touches `team-fde`'s Statsig path. A new group leaves Statsig alone and the `migrate` family still shows both: `wizard migrate statsig`, `wizard migrate resend` (several skill groups can share a `parentCommand`; `audit-events` and its siblings already do; [`audit-events/config.yaml`](https://github.com/PostHog/context-mill/blob/13c9d30/context/skills/audit-events/config.yaml)). Later vendors (`sendgrid`, `postmark`) become more variants of the same email group, which matches "other email services may follow".

## 5. Proof and the closing report

### How to prove a migration end to end on a sample Resend app

Layers, cheapest first. Test seams are what each layer can observe.

1. **Skill bundle (context-mill).** A vitest build test as #433 added: the skill builds, its reference files are present and the docs link resolves. Search ranking for "migrate from Resend", "replace resend with posthog" and "switch email provider" with the MCP `SkillCatalog` scorer, before and after, as #433 did.
2. **Fixture apps (wizard-workbench).** [wizard-workbench](https://github.com/PostHog/wizard-workbench) holds framework test apps with no PostHog installed ([`AGENTS.md`, "Companion projects"](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/AGENTS.md)). Add three small Resend fixtures:
   - **Happy:** Node (Express or Next.js route handler), `resend` plus `@react-email/components`, with a welcome email as an HTML string, a password reset as substitution-only React Email, and a webhook handler.
   - **Hard:** logic-heavy React Email (conditional, loop, `Date`), attachments, `batch.send`, `cc`, an idempotency key.
   - **Negative:** an app with no Resend. Expected result: stop before any edit.
     Use the three React Email demo templates and the probe from the [#528 prototype](https://github.com/Silthus/posthog/tree/prototype/react-email-templates/prototype/react-email-templates) as the first component fixtures.
3. **Agent run against the local stack.** Run the Wizard from a checkout with `--local-context-mill --local-mcp --local-posthog` (production builds reject them, [`AGENTS.md`, "Local dev targets"](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/AGENTS.md)) against the PostHog dev stack with both flags on and a locally verified sender. Headless `--ci` needs a personal API key and a gateway token ([`docs/local-dev.md`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/docs/local-dev.md#credentials-for-local-ci-and-headless-runs)). The harness has per-program e2e profiles: `<program>/test/e2e.json` read by [`e2e-harness/profiles.ts`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/e2e-harness/profiles.ts).
4. **Judge the diff, not the transcript** (the Wizard's own benchmark rule). Assertions on the working tree after the run:
   - Happy app: no `from 'resend'` left; `posthog.emails.send` count equals the old send count; the project typechecks; the template files exist; `.env.example` names the new key and the real `.env` holds it.
   - Hard app: every unsupported site is **unchanged** and has a report row with a reason; `resend` is still a dependency.
   - Negative app: empty diff.
5. **Dynamic proof.** Start the migrated happy app against the local stack and trigger each flow once. The dev mail catcher must show one mail per flow with the expected subject and recipient. This repeats #433's proof and needs the CDP worker.
6. **What stays a recorded gap:** real SES delivery and real DNS publish. They wait on the deployed-project proof the map already plans after merge. Sender verification through the MCP is unproven until [#116863 to #116865](https://github.com/PostHog/posthog/pull/116863) land ([#433 gaps](https://github.com/PostHog/context-mill/pull/433)).
7. **Cost and noise.** Model runs are not deterministic (n = 1 per cell is a sample, [`docs/benchmarking.md`](https://github.com/PostHog/wizard/blob/8e99848ae4a3b62e79ef96332dc720cb90b836e4/docs/benchmarking.md)). Run each fixture a few times and treat a failure that repeats as the signal.

### What the run reports to the person

The Wizard shows the outro and the report path. The report is the product here, because most of the work that is left belongs to the person. Proposed file: `posthog-migrate-resend-report.md` at the project root (the generic naming). Sections:

1. **Result line:** migrated N of M send sites; K left on Resend, with the count of each reason.
2. **Migrated sites:** file and line, old fields, new call, any warning (for example, "per-call `from` is now the template's sender").
3. **Left on Resend:** file and line, the unsupported field, what to do.
4. **Templates:** key, source path, uploaded or pending the first send, link to the library entry.
5. **Sender and domain:** each domain, status (verified, pending DNS), the Domain Connect link or record table, a note on coexisting with Resend's records, and the link to the UI wizard.
6. **Keys:** which env var was written to which file; the list of other places `RESEND_API_KEY` appears (CI, host, deploy config) where the person must add the PostHog key.
7. **Webhooks:** each Resend webhook handler found and the state ("no equivalent yet").
8. **Your next steps,** in order, each a checkbox: publish DNS; add the `phs_` key to staging and production; send a test email; deploy; then remove Resend. The last one is gated and tells the person not to do it early.

The Wizard must not commit. The report should say "review the diff with `git diff`".

## Recommended shape of the run

```text
npx @posthog/wizard migrate resend
  1. [Wizard, deterministic]  detect resend / @react-email in package files   -> stop early if none
  2. [Wizard]                 login (OAuth, family scopes) + AI approval gate
  3. [Agent, skill migrate-email-resend]
       inventory -> classify -> plan file
       preflight (flags, tools) -> sender check/create -> hand DNS to the person
       templates -> upload (source: repo/path/ref)
       key: wizard_ask(sensitive) -> set_env_values
       client setup (posthog-node) -> rewrite sites -> typecheck
       optional confirmed test send
       cleanup only when every site is migrated (gate 1) ; DNS/account removal left to the person (gate 2)
  4. [Wizard]                 outro + posthog-migrate-resend-report.md ; no commit
```

Decisions behind it:

- **A family command, a skill-driven run.** No new native program in the first version. Add the deterministic detector in a second Wizard PR, once the skill proves useful.
- **Replace what is mechanical, report the rest.** Never drop a field. Never delete `resend` while a site still uses it.
- **Two hand-offs are by design:** DNS and the `phs_` key. The run says so up front, so the person is not surprised at step 6.
- **Gate the destructive steps.** The Wizard's agent edits files directly, so the skill must ask before removing a dependency, and must not touch DNS or accounts.
