React Email templates in PostHog: render once, per send, or hybrid?

Each template below is sent the way a Resend user sends it today, react: <Template {...props} />, through three posthog-node sketches against an in-memory PostHog. The fake uses PostHog's real Liquid settings and the real content hash. Every email rendered here is real React Email output. The question: which path, or which mix, should posthog-node ship?

The developer's call site

Resend today

import { Resend } from 'resend'
import { WelcomeEmail } from './emails/welcome'

const resend = new Resend(process.env.RESEND_API_KEY)

const { data, error } = await resend.emails.send({
  from: 'Acme <hello@acme.com>',
  to: 'ada@example.com',
  subject: 'Welcome to Acme',
  react: <WelcomeEmail name="Ada" />,
})
  • The SDK renders the element to HTML on every send and posts only HTML.
  • Resend keeps no template for it.

A. Render once with Liquid placeholders

import { PostHog } from 'posthog-node'
import { WelcomeEmail } from './emails/welcome'

const posthog = new PostHog(KEY, { secretKey: process.env.POSTHOG_SECRET_KEY })

const { data, error } = await posthog.emails.send({
  from: 'Acme <hello@acme.com>',
  to: 'ada@example.com',
  template: posthog.emails.reactTemplate(WelcomeEmail, {
    key: 'welcome',
    subject: 'Welcome to {{ variables.name }}',
  }),
  data: { name: 'Ada' },
})
  • The SDK renders WelcomeEmail once, with every prop set to "{{ variables.<prop> }}", hashes it, and uploads it by key when PostHog lacks that hash.
  • Each send posts only the key, the hash and data. PostHog fills the Liquid.
  • Props become data. Data must be JSON: no Date, no React elements, no functions.

B. Render per send

const { data, error } = await posthog.emails.send({
  from: 'Acme <hello@acme.com>',
  to: 'ada@example.com',
  subject: 'Welcome to Acme',
  react: <WelcomeEmail name="Ada" />,
})
  • Same as Resend, character for character, apart from the client.
  • The SDK renders HTML and plain text and posts both. The send route needs inline subject, html and text.
  • PostHog keeps no template: nothing in the library, no preview, no edit with your agent, no content hash.

C. Hybrid: render per send, listed in the library

const { data, error } = await posthog.emails.send({
  from: 'Acme <hello@acme.com>',
  to: 'ada@example.com',
  subject: 'Welcome to Acme',
  react: <WelcomeEmail name="Ada" />,
  template: 'welcome',
})
  • B plus one field. The SDK renders the real props for the recipient, and renders WelcomeEmail.PreviewProps once per process for the library.
  • The send posts the inline HTML and text plus template: { key, hash }. The hash is the preview render, so it changes only when the component changes.
  • A hash PostHog lacks answers 409; the SDK uploads the preview render with its source path and retries once, as posthog-node does for HTML files.
  • Without template, it is B.

posthog-node has no from yet (#522 lists it as a gap). The call sites show it for a like-for-like read.

What the comparison shows

A. Render once with Liquid placeholders

  • Pure substitution works. Koala, Dropbox and Vercel send the same text as Resend. Each send posts 170 to 460 bytes, the hash is stable across renders, and PostHog holds a real Liquid template that a workflow or the UI could send with other data.
  • PostHog's renderer handles the escaping that #522 flagged. It decodes entities inside {{ }} before Liquid runs and escapes the output, so & in a URL and ' in a name come out right.
  • A Date or array prop throws at render. Yelp's Intl.DateTimeFormat and Stack Overflow's tips.map fail on a placeholder string. Number formatting fails the same way. This failure is loud and early.
  • A conditional sends the wrong email with no error. The stored template keeps the branch that the placeholder took. In the probe, a Pro customer gets the free-plan text.
  • An optional prop makes the template depend on the call. A send with coupon stores a template with the coupon line. The next send without it uploads a template without the line and replaces it. From then on, a send with a coupon gets the current content, so the line is gone and the only signal is a template_superseded warning. Run bun run optional-prop to see the three sends.
  • <Preview> pads the preheader to 200 characters and counts the placeholder's length. After the fill, the padding is short (20 characters for Vercel, 17 for the probe), so body text can show in the inbox preview. This is cosmetic, and the SDK could fix it.
  • The automatic check (substitution only? then A, otherwise C) passes the probe and sends the wrong email. It proves equality only for the PreviewProps, so a branch they never reach stays hidden. An automatic mix is not safe as a default.

B. Render per send

  • Same as Resend for all six templates, and the call site is Resend's apart from the client.
  • The send route needs inline subject, html and text. That reverses the template-only send of the 2026-10-16 re-chart.
  • Each send posts the full HTML (4 to 11 KB here), and the queued send carries it.
  • Inline HTML gets no Liquid pass, so a {{ in a person's data stays literal (the probe's name shows this).
  • It loses the template library entry, the preview, "Managed by code", edit with your agent, the content hash, and per-template delivery stats.

C. Hybrid

  • Same as Resend for all six templates. The call site is B plus template: 'welcome'.
  • The library gets an entry from the PreviewProps render with its source path, so "Managed by code", the read-only preview and edit with your agent keep working. The hash changes only when the component changes, and the upload uses the 409, upload, retry once loop that posthog-node already has for HTML files.
  • Costs: the send route takes inline HTML next to template. Each send is about 120 bytes bigger than B. The SDK renders each component once more per process.
  • The preview shows sample data, not each email: the probe's entry shows the free plan. An entry like this has no Liquid, so a workflow or the UI can't send it, and the route must refuse a send by key alone.
  • The key must be explicit. A minifier renames Component.name, so the SDK can't derive the key from it.
  • <Preview> also writes a <title>. posthog-node reads the subject of an HTML file from <title>, so a React send needs an explicit subject, or the preheader becomes the subject.

My read

Ship C as the only React path: react plus an optional template. Without template it is B. Keep Liquid for HTML template files, and don't ship A for React. If a team later needs a React template that a workflow sends, A can come back as an explicit opt-in that refuses Date and array props. It should never be an automatic pick. Smallest PR order: inline content on the send route and react/html in posthog-node (B), then template next to inline content (C).
