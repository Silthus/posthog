1. Question

EmailService.executeSendEmail (services/messaging/email.service.ts:368-709) is one 340-line method. It runs three send gates, a sender check, a tracking decision, two pacing claims, a provider switch, three copies of the reschedule logic and the outcome bookkeeping, all by mutating one result object. PostHog/posthog#112295 fixed a bug that hid in that shape: one of the three reschedule copies forgot to re-attach queueParameters, so a throttled email was silently dropped, and no test noticed because no test crosses the queue.

This brief proposes how the method splits into small steps and submodules while EmailService stays a deep module with one public method, which seams the outside-in tests drive, which cases are missing, how the behavior-preserving refactor lands as PRs after the test harness, and which comments survive. The open sandbox-sender stack (PostHog/posthog#111904 → #112071) adds about 400 more lines to the same method, so the design shows where that lands too.

Interface (everything a caller must know, unchanged by the refactor):

  • Throws in exactly three places: queueParameters.type is not email; the integration lookup rejects (step 0, outside the try; M10); the engagement-config read rejects after the outcome is known, possibly after the provider accepted (step 12; M19). Every other problem becomes an outcome.
  • A reschedule re-attaches the original params, not the UTM-tagged or tracked HTML: the retry prepares the content again.
  • Exactly one outcome per call. Its footprint on the result is fixed by section 6.
  • Rescheduled ⇒ finished: false, queueParameters equal to the input's, queuePriority equal to the input's, queueScheduledAt in the future, no metric, no VM push, no event.
  • Test send ⇒ gates apply, pacing does not, no metric, asset or event.
  • Not undone on a later reschedule or failure: a workflow pacing token stays spent when the team cap then denies, and both stay spent on a provider throttle (map follow-up "refund on throttle"). Shadow-mode partial claims stay spent. The global SES dequeue token is spent before the method runs at all (services/cyclotron-v2/worker-rate-limited.ts:42-70).
  • Cost per call: 1 integration read, 1 suspension read, up to N suppression reads and N consent reads (N = recipients), up to 3 Valkey claims (2 in enforce mode; shadow mode claims the two cap buckets separately), 1 provider call, and 1 engagement-config read on sent or failed.

5.3 The method after the refactor

public async executeSendEmail(invocation, isTest = false) {
  const send = startSend(invocation, isTest)                       // asserts email params, keeps priority
  const integration = await this.integrationManager.get(selectEmailSenderIntegrationId(invocation.id, send.params.from))
  const outcome = await this.runSend(send, integration)
  await applyOutcome(send, outcome, () => this.teamWorkflowsConfig.shouldCaptureEngagementEvents(invocation.teamId))
  return send.result
}

private async runSend(send: EmailSend, integration: IntegrationType | null): Promise<SendOutcome> {
  let trackingEnabled = true
  try {
    const stopped = await this.gates.stoppedByTeamOrWorkflow(send)
    if (stopped) return stopped
    const from = resolveSender(integration, send)
    const suppressed = await this.gates.suppressed(send)
    if (suppressed) return suppressed
    trackingEnabled = await this.tracking.decide(send)
    const delayed = (await this.workflowPacing.claim(send)) ?? (await this.teamCap.claim(send))
    if (delayed) return delayed
    const params = withUtmTags(send, this.siteUrl)
    await this.providerFor(integration).deliver({ send, params, from, trackingEnabled })
    return sent(send, params, from, trackingEnabled, this.messageAssets)
  } catch (error) {
    return error instanceof SESThrottleError
      ? { kind: 'rescheduled', cause: 'provider_throttle', delayMs: error.retryAfterMs }
      : { kind: 'failed', error: error.message, trackingEnabled }
  }
}

Invariants this shape enforces by construction: one reschedule writer (the #112295 bug class cannot recur per cause), gates before any token spend (order is visible in eight lines), and a step cannot both skip and send.

A watcher-degraded run (priority 2) can return to the hogflow queue at 0 or 1 and jump ahead. Read from the code, not reproduced; card C13 and M17.

13. Decision cards

Open

C1 · Outcome modelopen

How steps report what happened.

  1. A SendOutcome union and one applyOutcome writer. Steps return values; one place writes queue fields, metrics, VM stack and events. Kills the reschedule bug class, and section 6 becomes the code's own shape. Cost: a new type, and R3 touches every exit.
  2. Keep mutating result, but extract reschedule(result, params, delay) and skip(result, reason) helpers. Smaller diff; the matrix stays implicit, and a new exit can still forget a field.
Recommend 1. The bug that started this map is exactly "one exit wrote a different footprint".

C2 · Constructor wiringopen

  1. One EmailServiceDeps object; EmailService builds its submodules inside. Named fields, optional limiters read as "off". Touches two production call sites and the tests (R1).
  2. Keep 11 positional params (13 with sandbox). Zero churn; tests keep passing undefined, null, limiter by position.
  3. Inject the built submodules (gates, pacers, providers). Maximum swapability, but each has one adapter: a hypothetical seam, and tests have no use for it.
Recommend 1.

C3 · Gate shapeopen

  1. Explicit calls in runSend to a small EmailSendGates class. Order readable in one place; the sender check sits between gates naturally.
  2. A SendGate[] pipeline. Uniform and extensible, but the sender check (fails, not skips) breaks the uniform shape, and every gate has one implementation.
Recommend 1. YAGNI on the pipeline until gates multiply beyond the sandbox ones, which C4 already scopes to the provider.

C4 · Provider seamopen

  1. EmailProvider interface with SES and maildev adapters, chosen by integration.config.provider. Two real adapters today, a third (sandbox) in flight, and a provider-neutral throttle contract.
  2. Keep provider methods private on EmailService, and only extract a pure buildSesSendEmailInput. Less structure; the sandbox stack keeps branching inside the SES method.
Recommend 1. Two adapters make it a real seam.

C5 · Queue-level seam for the round-tripopen

  1. HogFlowExecutorService.execute in a loop, passing result.invocation back in. Existing pattern (hogflows/hogflow-executor.service.test.ts:3036); skips worker flow loading and the job codec.
  2. Email worker processInvocations with a codec hop through invocationToV2JobInit / v2JobToInvocation between attempts. Real worker, flow reload, and the persisted shape; still no Postgres queue I/O.
  3. Real cyclotron Postgres queues and workers in the existing workflows-e2e.serial.test.ts email suite (setup at :2832-2855; it already covers routing and pacing parks, with maildev). Highest fidelity, including the reschedule SQL; serial, slower, and its pacing cases only assert the park, never the later send.
Recommend 2 for M1-M4 and M17, plus one case of 3 for M1 against the SES fake: a throttle waits under a second, so the full production path costs little, and it is the exact bug that started this map.

C6 · Rate limiter in S1 testsopen

Recommend 1, with S3 owning the exact numbers.

14. Blast radius

  • What can break: every workflow and destination email send. Worst cases: a reschedule that drops the email (M1-M3 guard it), a skipped send that bills differently (M9), a gate moved after a token claim (L4), a lost SES header (tenant, tracking code, unsubscribe) that breaks reputation attribution or the webhook.
  • Who notices: customers (emails missing or late, wrong run-log lines), the SES webhook (missing tracking header), billing (skip flag), on-call (throttle and park metrics).
  • Mitigation: each slice runs S1 and S2 against the SES fake; R3 gets a qa-swarm (send path is a danger area); merge-risk on every PR.
  • Out of scope: pre-send skips in HogFunctionHandler, the hog executor loop, push notifications, the refund-on-throttle and give-up-limit follow-ups, the real-SES test.
